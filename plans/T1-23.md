# T1-23 슬롯 추출 필드별 정확도 평가

## Goal
- 완료 기준 (TASK.md 그대로): 골든 `required_facts`에서 질문 유형·항목·기간·분류 슬롯 정답을 도출하고, 필드별 정확도를 하네스에 추가해 측정한다
- Baseline: **슬롯 채점 없음**(`eval/`에 슬롯 코드 0건). 질의 이해는 `wrong_dims`·`wrong_period` 오류로만 간접적으로 보인다.
  이 오류는 계산 결과(답의 fact)를 보고 매기므로, 파싱이 틀렸는지 계산이 틀렸는지 구분되지 않는다.
  측정 대상 실행: `eval/results/20261025-120211-701208-C-stat-chart` (C, HCX-DASH-002, 40문항)

## Idea
정답 슬롯을 따로 라벨링하지 않는다. 골든의 정답 셀 ref에서 기계적으로 뽑고, 파이프라인이 답마다 남기는 `StatAnswer.query`(StatQuery)와 비교한다.

| 필드 | 정답 (골든 required 셀) | 예측 (`StatAnswer.query`) | 맞음의 기준 |
|---|---|---|---|
| 유형 | `item.type` | `query.type` | 같음 |
| 항목 | 셀의 항목 라벨 + 이름에 "항목"이 든 분류축 라벨(DT_1B8000F `기본항목별`) | `item`·`items` + 같은 축의 `filters`·`targets` | 라벨 집합이 같음 |
| 분류 | 나머지 분류축별 라벨 집합 | `filters` ∪ `targets` | 축별 라벨 집합이 같음 |
| 기간 | 정답 셀 시점의 처음·끝 | `query.periods`의 처음·끝 | 처음·끝이 같음 |

| 순위 축 (최대최소만) | 1위 셀의 라벨이 질문에 없는 축 (시점이면 `시점`) | `query.over`의 키 (시점 순위는 to_query가 over를 비워 둠 → 빈 over + pick 있음을 `시점`으로 봄) | 같음 |

정규화 규칙:
- 라벨은 공백과 끝의 단위 괄호를 지우고 비교한다(`1인 (가구)` = `1인`, `합계출산율(명)` = `합계출산율`).
- **표에서 라벨이 하나뿐인 축은 양쪽에서 뺀다.** DT_1B8000F의 항목 축(`T1` 하나)은 예측 item이 None이고, DT_101094A001의 '비율'은 예측에 들어간다. 골든 fact.dims도 이런 축은 적지 않는다.
- **합계 라벨(`is_total`)은 비교 유형이 아닐 때만 정답에서 뺀다.** 비율의 분모(`일반가구_계`)나 질문에 없는 분류의 기본 합계는 슬롯이 아니다. 반면 "전국보다" 같은 비교 문항에서 `전국`은 기준 쪽 슬롯이므로 남겨서 채점한다.
- 기간은 정답 셀 시점의 **min·max**와 예측 시점의 min·max를 비교한다(골든 셀 순서는 시간순이 아님). "2015년부터 2020년까지"에 파이프라인은 6개 시점을 다 담고, 골든은 두 끝만 정답으로 갖기 때문이다.
- 최대최소: 순위 축은 분류·기간 비교에서 빼고 위의 "순위 축" 필드로 따로 채점한다. 1위 라벨(세종특별자치시 등)은 답이지 슬롯이 아니기 때문이다.
- 대상: 정답 셀이 있는 `answerable`·`default_allowed`(C 실행 기준 28문항: 값 6·추이 5·비교 5·비중 4·최대최소 5·기본값 3). 거절·되묻기는 거절 사유 채점이 이미 있어 뺀다.
- **예측이 비었으면 전부 틀림**: 실행 실패이거나 query의 type·item·periods·filters·targets가 모두 비어 있는 경우다(예비 챗봇은 query 객체를 남기되 값이 비어 있음, VAL-03). 이걸 먼저 걸러야 빈 분류가 합계만 남은 정답과 우연히 맞는 일이 없다.
- **StatQuery의 기록 한계**: `to_query`는 비교가 아닌 문항에서 라벨이 2개 이상인 축을 filters에 남기지 않는다("서울·부산 추이" 같은 문항). 이런 문항은 계획이 맞아도 분류가 틀림으로 나온다. 채점기에서 덮지 않고, 해당 문항을 리포트에 "기록 한계"로 따로 세어 파이프라인 쪽(to_query) 수정 대상으로 넘긴다.

슬롯 결과는 **판정(PASS/FAIL)에 영향을 주지 않는** 별도 지표다.

## Option A — 결정적 비교를 채점기에 넣기
- 접근: `eval/grade.py`에 `slot_checks(item, answer, cells)`를 추가하고, `Grade`에 선택 필드 `slots`(필드별 참·거짓)를 붙인다. `eval/harness.py` 요약에 필드별 정확도와 "네 필드 모두 맞음" 비율을 넣는다. `eval/grade_run.py`는 `decision_metadata.route`로 규칙 경로와 LLM 보완 경로를 나눠 한 줄 더 적는다. pytest: 골든 슬롯으로 만든 query는 4/4가 나오는지, 필드 하나씩 틀린 query는 그 필드만 틀리는지.
- 예상 성능 향상: 슬롯 지표 없음 → 필드 5개 측정. C 실행(28문항) 예상치: 유형 ~25/28, 항목 ~24/28, 분류 ~21/28, 기간 ~26/28, 네 필드 모두 맞음 ~19/28 (근거: 예비 챗봇 1문항은 전부 틀림, 리뷰에서 기본값 3문항·끝점 맞춤 추이 문항의 기간 일치를 확인, 분류는 동부 등 놓친 문항과 기록 한계 문항이 깎임). 최종 수치는 실측으로 확정.
- 실질 반영 이점: 평가 기준 3위 "질의 이해"를 처음으로 직접 잰다. 실패가 파싱 탓인지 계산 탓인지 갈린다(슬롯은 맞는데 FAIL = 계산·문장 문제). 결정적이라 T1-24 회귀 게이트에 그대로 들어간다. T2-16(Gemma vs HCX 슬롯 비교)의 측정 도구가 된다.
- 비용·리스크: 반나절, LLM 0. 순위 축 정답을 "1위 라벨이 질문에 없는 축"으로 정하므로 줄임말에 약할 수 있다(최대최소 5문항이라 손검사로 확인). `Grade` 필드가 늘어 T1-24 채점기 해시가 바뀐다(기준선을 아직 고정하지 않았으므로 영향 없음).

## Option B — 골든에 슬롯 정답 필드를 명시
- 접근: A의 비교를 쓰되, 정답 슬롯을 채점 때마다 뽑지 않고 build 스크립트가 골든에 `slots` 필드로 써 둔다. 사람이 검토·수정할 수 있고, 최대최소의 순위 축을 명시할 수 있다.
- 예상 성능 향상: A와 같은 지표 + 정답 슬롯 오류를 사람이 고칠 수 있음.
- 실질 반영 이점: 정답이 눈에 보이는 형태로 남아 발표·리뷰에 좋다.
- 비용·리스크: 하루. 골든 본문에 넣으면 `GoldenItem` 계약이 바뀌고 골든 sha256이 바뀐다. 별도 사이드카 파일(`stat_golden.slots.jsonl`)에 두면 이 문제는 없지만, 골든과 사이드카를 함께 관리·배포해야 한다.

## Option C — LLM이 슬롯 동치를 판정
- 접근: 정답 슬롯과 예측 슬롯을 LLM에 주고 같은 뜻인지 판정시킨다(줄임말·동의어 흡수).
- 예상 성능 향상: 줄임말로 인한 거짓 오답이 줄어든다.
- 실질 반영 이점: 라벨 표기 차이에 강하다.
- 비용·리스크: 비결정적이라 회귀 게이트에 못 넣는다. 실행마다 호출 비용. 예측 라벨은 이미 표 라벨로 정규화돼 나오므로(`to_query`가 표 라벨을 씀) 동의어 문제가 실제로는 작다 → 얻는 것보다 잃는 것이 크다.

## Recommendation
**옵션 A**. 파이프라인의 StatQuery가 이미 표 라벨을 쓰므로 문자열 비교로 충분하고, LLM 비용 없이 결정적이라 회귀 게이트까지 바로 이어진다. 골든 계약도 바꾸지 않는다. 최대최소 순위 축 판별처럼 약한 부분은 사람 확인으로 메운다.
