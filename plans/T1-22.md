# T1-22 단계별 로그 (OpenTelemetry span 단위로 이식 가능하게)

## Goal
- 완료 기준 (TASK.md 그대로): 판정·슬롯 추출·계산·검증·재생성·템플릿 대체 단계별 로그와 실패 건수를 남긴다. 로그 단위는 Phase 2에서 OpenTelemetry span으로 옮길 수 있게 정한다(기존 범위: 단계별 입력 토큰·출력·모델·지연 기록, 골든셋 실행 결과와 연결)
- Baseline: 단계별 지표 없음. 지금은 질문 단위 합계(`latency_seconds`, `usage`)와 최종 경로(`decision_metadata.route/compose`)만 `results.jsonl`에 남고, LLM 호출 단위 기록(`events.jsonl`의 `generate_*`)은 어느 단계 호출인지 알 수 없다.

## Idea
`StatPipeline.ask`([kosis_chat/pipeline.py](../kosis_chat/pipeline.py))의 각 단계를 span 모양 dict 하나로 기록한다.

- span 필드: `name, start_ms, duration_ms, status("ok"|"error"), attributes` — OTel span의 이름·시작·길이·상태·속성과 1:1 대응. 질문 1회 = trace 1개, 부모는 질문 루트(평면 리스트, 순서 = 실행 순서).
- 단계 이름: `judge` → `analyze.rules` → `analyze.llm_fill`(규칙이 못 채울 때만) → `compute` → `compose`(시도마다, `attempt` 속성) → `verify`(시도마다) → `template`(대체 시) / `fallback_chatbot`(경로 이탈 시).
- LLM span 속성은 OTel GenAI 표준 이름: `gen_ai.request.model`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `llm.attempts`, `llm.status`.
- 저장: `decision_metadata["spans"]` → 이미 `results.jsonl`로 흘러가 골든셋 `question_id`와 연결된다. 새 파일·새 의존성 없음.
- 집계: [eval/grade_run.py](../eval/grade_run.py) report.md에 단계별 표(실행 수·실패 수·지연 p50/p95·토큰 합) 추가. `grade_run.py`는 `GRADER_FILES`에 없어 회귀 게이트 해시에 영향 없음.

## Option A — span 모양 dict 직접 기록 (최소안)
- 접근: 위 Idea 그대로. 15줄 contextmanager(`_span`) + 각 단계 감싸기 + grade_run 집계 함수.
- 예상 성능 향상: 단계별 관측 지표 0개 → 6단계 × (실패 수·p50/p95·토큰). 답 품질 지표(PASS 수)는 변화 없음(로그만 추가).
- 실질 반영 이점: 기술 설계·결과 검증 항목. T1-15 "실패 유형별 건수"의 근거 숫자, T2-15에서 dict→OTel span 변환만 하면 됨.
- 비용·리스크: 반나절. LLM 비용 0(mock 측정). `decision_metadata`가 커지는 것 외 리스크 낮음.

## Option B — OpenTelemetry SDK 즉시 도입
- 접근: `opentelemetry-sdk` 추가, tracer로 span 생성, 파일 exporter로 jsonl 저장.
- 예상 성능 향상: A와 같은 지표 + Phase 2 이식 작업 0.
- 실질 반영 이점: Jaeger 연결이 바로 가능.
- 비용·리스크: 의존성 추가, exporter·context 전파 설계를 T2-15보다 먼저 해야 함. 마감(10/27) 초과 위험.

## Option C — events.jsonl에 단계 이벤트 추가
- 접근: `RunRecorder.event`로 `stage_started/stage_ended` 기록, 파이프라인에 recorder 훅 주입.
- 예상 성능 향상: A와 같은 지표, 기존 `generate_id`와 시간순 결합.
- 실질 반영 이점: LLM 원문 호출과 단계가 같은 파일에 있음.
- 비용·리스크: 파이프라인이 평가 recorder에 의존하게 됨(런타임 챗봇에선 로그 없음). 연결 코드 증가.

## Recommendation
옵션 A. 이슈 요구는 "옮길 수 있는 단위"이고 OTel 도입 자체는 T2-15 범위. 기존 `results.jsonl` 통로를 재사용해 diff가 가장 작다.

1. mock에서는 `usage`가 비고 지연이 0에 가까움 → **반영**: mock으로는 단계별 실행·실패 건수만 측정. 지연·토큰은 HCX 실행 1회로 채우거나 "측정 안 함"으로 적는다.
2. 거절과 실패를 섞지 말 것 → **반영**: `rules_final`·`calc_refused` 거절은 `status: ok` + `outcome` 속성. LLM 형식 오류와 verify 문제는 `status: error`.
3. contextmanager 대신 호출 지점에서 span을 쌓는 더 단순한 방식 → **반영**: `_Calls.span()` 메서드 하나로 기록. `_ask_model`에 `stage` 인자 추가.
4. 함정 → **반영**: (a) fallback 경로가 `llm_fill` 토큰을 버리는 기존 버그 → usage 합산으로 수정하고, chatbot 내부는 `fallback_chatbot` span 하나로 기록. (b) `promptTokens/completionTokens`를 GenAI 이름으로 옮기고, 모델명은 `settings.model_name`에서 가져온다. (c) LLM span `duration_ms`에서 sleep·재시도 대기를 뺀다(`Answer.latency_seconds`와 같은 기준).
5. 조기 반환 2곳의 span, compose가 break할 때 verify span이 없는 경우 → **반영**: `_done`에서 일괄 첨부한다. verify는 compose 시도와 `attempt`로 짝짓고, verify span이 없는 경우는 정상으로 둔다.
