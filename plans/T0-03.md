## Idea
- 범위 (T0-01 미완료에 대한 결정 b): `src/kosis_ai/__init__.py`와 `src/kosis_ai/schemas.py`만 만든다.
  uv 전환·ruff·디렉터리 전체 골격은 T0-01에 남긴다. `requirements.txt`에 `pydantic>=2`, `pytest.ini`의 `pythonpath`에 `src`.
- 필드 출처 (새로 발명하지 않는다):
  1. 골든셋 v0 형식 (T1-03): fact `{id, value, unit, period, dims, source_ref, raw, derivation, round, note}`,
     문항 종류 4개, 거절 사유 8개 (`no_period`·`no_item`·`class_mismatch`·`unit_mismatch`·`not_aggregatable`·`causal`·`missing_value`·`out_of_scope`),
     `allowed_reasons`(허용 사유 목록), `clarify_options`, `default_applied`.
  2. 실전 1 PLAN (docs/plans/20261020-stage1-table-summary/PLAN.md, **DRAFT rev 3** — 미확정): 질문 분석 출력(D-003),
     `measure_kind`, LLM 출력 `plan` = fact/text 항목, 결합 검증 V1~V5.
- 모델 대응:
  - `StatQuery` — 질문 분석 결과 (T1-06 출력): 유형 5종, 시점, 분류 조건, 항목, 모호성.
  - `Fact` / `StatResult` — 코드가 계산한 fact 목록 (T1-07 출력). 숫자는 여기에만 있다. 골든 fact도 같은 모델로 읽는다.
  - `Source` — `KOSIS / 조사명 / 통계표명 (+링크)`. 문자열 렌더링은 코드가 한다(모델 생성 링크 금지, model-candidates.md 8.1).
  - `Refusal` — 사유 코드 1개 + 이유 문장 + 가능한 범위 안내 (T1-08 출력).
    채점: 답변의 `reason`이 골든 `allowed_reasons`(없으면 `[refusal_reason]`)에 들어 있으면 정답 → scorer `wrong_reason` 판정 기준.
  - `StatAnswer` — `summarize_stat()` 반환 (T1-11, T3-01 툴 반환값): 답변 / 거절 / 되묻기 + 출처.
- 상수 원본은 `schemas.py` 한 곳. `eval/scorer.py`의 `KINDS`는 T1-04에서 schemas를 import하도록 바꾼다(이번 범위 밖, 중복은 그때 제거).
- 실행 기록(V1~V5 결과, 재생성 횟수, 템플릿 대체)은 공개 계약이 아니라 내부 로그라 `StatAnswer`에 넣지 않는다. T1-10에서 별도 모델로 추가해도 기존 스키마를 깨지 않는다.

## Option A — 골든 형식 그대로 (평면, 타입 검사만)
- 접근: 5개 모델을 골든 필드에 1:1로 맞추고, 골든에서 빠질 수 있는 필드는 모두 선택(Optional). 모델 간 교차 검증 없음.
  `StatAnswer` = `outcome` + `text` + `facts` + `refusal` + `source` 평면 구조.
- 예상 성능 향상: 골든 fact 적합률 0/98 → 98/98. 잘못된 입력 차단 0 → 약 3건(타입·Literal 위반만: 없는 유형, 없는 사유 코드, 값이 문자열).
- 실질 반영 이점: T1-04 하네스가 골든 fact와 답변 fact를 같은 모델로 비교할 수 있다.
- 비용·리스크: 1시간. "거절인데 사유 없음", "답변인데 출처 없음", "없는 fact를 참조"가 모두 통과한다 → 그 검사가 T1-08·T1-10·하네스에 흩어진다.
  LLM 답변 구성(`plan`)을 담을 자리가 없어 T1-09에서 `StatAnswer`를 다시 열어야 한다.

## Option B — A + 답변 구성 + 교차 검증 (계약을 스키마에서 강제)
- 접근: A에 다음을 더한다. 추가 필드는 모두 선택이라 골든 읽기를 깨지 않는다.
  - `Fact`: `measure_kind`(선택), `derivation`·`round`, `raw`, `note`. 검증: 원본 셀 fact는 `source_ref` 필수, 계산 fact는 `derivation` 필수 (둘 중 하나, 메모 fact 제외)
  - `AnswerPart` = `{kind: "fact", fact_id}` | `{kind: "text", text}` — LLM은 이 목록만 고른다
  - `StatAnswer` 교차 검증:
    - V1: `parts`의 모든 `fact_id`가 `facts`에 있다
    - `outcome="refused"` ↔ `refusal` 필수, `outcome="clarify"` ↔ `clarify_options` 2개 이상
    - `source` 필수 — 단, 거절 사유가 `out_of_scope`면 예외 (CLAUDE.md "모든 답에 출처")
    - `default_applied`: 기본값을 쓴 조건 기록 (`default_allowed` 문항 채점용)
  - text 항목의 숫자 금지(V4)는 정규식 판정이 필요해 T1-10 검증기에서 한다. 스키마는 막지 않는다.
- 예상 성능 향상: 골든 fact 적합률 0/98 → 98/98. 잘못된 입력 차단 0 → 약 9건
  (A의 3건 + 없는 fact 참조, 거절인데 사유 없음, 되묻기인데 선택지 없음, 출처 없음, out_of_scope 출처 예외 허용 확인, 근거 없는 fact).
  다음 단계: 결합 검증 V1~V5 중 V1을 스키마가 맡는다(근거: PLAN의 V1 정의가 참조 존재 검사). V2~V5는 T1-10.
- 실질 반영 이점: 데이터 정확성·예외 처리·결과 검증. T1-06~T1-11이 같은 모델을 import해서 실전 1 동안 스키마를 다시 열 일이 거의 없다.
- 비용·리스크: 2~3시간. 실전 1 PLAN이 DRAFT라 `AnswerPart`가 B1 확정 때 바뀔 수 있다. 바뀌는 부분은 `AnswerPart` 한 곳이라 영향 범위가 좁다.

## Option C — 결과별 분리 타입 + 엄격 모드 + JSON Schema 내보내기
- 접근: B의 필드를 쓰되 `StatAnswer`를 `Answered | Refused | NeedsClarification` 판별 유니온으로 나눠 잘못된 조합을
  타입 자체로 막는다(교차 검증기 대신). 런타임 모델은 `extra="forbid"`, `frozen=True`. 골든 읽기는 별도 느슨한 모델(`GoldenFact`)로 분리.
  `model_json_schema()`로 `docs/schemas/*.json`을 내보내 HCX 구조화 출력 프롬프트에 쓴다.
- 예상 성능 향상: 골든 fact 적합률 0/98 → 98/98 (`GoldenFact` 경유). 잘못된 입력 차단 0 → 약 11건(B + 모르는 필드, 수정 시도).
  T1-06 JSON 파싱 성공률에 줄 영향은 추정 불가 (HCX 구조화 출력 지원 여부 미확인, PLAN [NEEDS CLARIFICATION]).
- 실질 반영 이점: 기술 설계. 종합 단계 툴 정의를 스키마 파일로 바로 등록할 수 있다.
- 비용·리스크: 4~5시간, 오늘 마감 초과 가능. 런타임 `Fact`와 `GoldenFact` 두 모델이 생겨 하네스 비교에 변환이 필요하다.
  JSON 내보내기는 B 위에서도 `model_json_schema()` 한 줄로 나중에 할 수 있다.
