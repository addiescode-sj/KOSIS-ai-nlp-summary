# T0-03 v2 공용 스키마 강화 (브랜치 T0-03-schemas_v2)

v1(2026-10-22, 아래 "v1 기록")은 완료됐다. v2는 같은 계약(`src/kosis_ai/schemas.py`)을 10/24~26 C 파이프라인 90문항 결과에서 드러난 빈틈에 맞춰 강화한다.
점검 기록: 사용자 작업 폴더 `plans/20261026-t0-03-schemas-v2/01-inspection.md`(E1~E14 상태, 실행 13개, 90문항 FAIL 분해).

## Goal
- 완료 기준: 공용 계약이 **틀린 답·틀린 기록을 만들 수 없게** 막고(오타 필드, 모델이 쓴 숫자를 코드가 썼다는 기록, 중복 셀), 지금 계약으로 **표현할 수 없는 질문(복합 연산)과 출력(그래프)** 을 담는다. 예전 결과(`eval/results/*/results.jsonl`의 `stat_answer`)는 계속 읽힌다.
- Baseline (실행 20261026-160620, 90문항, HCX-DASH-002, oracle scope, compose-v1):
  - 수치 정확도 32/66 (48%), 거절 18/20, 잘못된 거절 0
  - 예비 챗봇(fallback)으로 간 17문항 중 숫자 출처 기록이 맞는 것 0/17 (`decision_metadata.numbers_origin`이 모두 `code`)
  - 그래프가 공용 계약(`StatAnswer`) 안에 있는 답 0/53 (`Answer.chart` dict에만 있음)
  - 복합 연산(S-CX, op=AVG·SUM·PAVG·GAP·GRW·SHR·VSA·MON·PRD) PASS 0/24
  - 모르는 필드를 막는 공용 모델 0/11 (`extra` 기본값 ignore)
  - 계약 위반 차단 테스트 18
  - 한 문항의 코드 예외가 90문항 실행 전체를 멈춤 (E2)

## Idea
지금 계약의 빈틈은 세 종류다.
1. **느슨함**: 오타 필드가 조용히 사라지고, `decision_metadata`가 자유 dict라서 "모델이 쓴 숫자를 코드가 썼다"는 기록(E1)이 통과한다. 기본 시점을 확인 없이 기록(E14)해도 막을 장치가 없다. 같은 `source_ref`의 셀 두 개가 계산 색인에서 조용히 덮어쓴다(E13).
2. **표현 못 하는 질문**: `QuestionType` 다섯 개(value·trend·compare·share·extreme)로는 "5년 평균", "누적합", "두 기간 평균 비교", "비중이 몇 %p 늘었나", "최근 값 vs 직전 n년 평균", "상반기 합"을 `CalcRequest`로 쓸 수 없다. 분석이 포기하고 fallback으로 가거나(16개) 처음·끝 시점만 써서 틀린다(14개).
3. **빠진 출력**: 최종 출력은 "자연어 + 그래프"인데 그래프가 공용 계약 밖에 있다.

공통 원칙: 예전 결과를 계속 읽는다(새 필드는 모두 기본값; `numbers_origin=None`이 v2 이전 기록). 숫자는 코드가 계산하고 LLM은 문장만 쓴다. 새 연산은 T1-25 연산 목록(10종)을 기준으로 하고 40문항에만 맞춘 규칙은 만들지 않는다.

## Option A — 계약 엄격화 + 숫자 출처 기록 (S1~S4, S10, S11)
- 접근: 공용 모델을 엄격하게 하고, 답마다 "숫자를 누가 썼고 코드가 검증했는지"를 계약 필드로 남긴다. 계산·분석 로직은 건드리지 않는다.
- 예상 성능 향상: fallback 기록 정확도 0/17 → 17/17 (fallback 답은 FactPart가 없어 S4 규칙상 `code`를 쓸 수 없음). 계약 위반 차단 테스트 18 → 약 30. 수치 정확도는 32/66 그대로.
- 실질 반영 이점: 이후 모든 실험의 기록을 믿을 수 있다. 2단계·종합이 `numbers_verified`로 "검증된 숫자만 보여 주기"를 할 수 있다.
- 비용·리스크: 반나절. 엄격해진 검사 때문에 지금 통과하던 답이 ValidationError가 날 수 있다 → S11로 문항 단위로 가두고, 저장된 90문항 결과를 새 계약으로 다시 읽는 검사로 먼저 확인한다.

## Option B — A + 그래프 계약 + 복합 연산 (S1~S8, S10, S11)
- 접근: A에 더해 그래프를 공용 계약에 넣고(S5), 파싱은 되는데 연산이 없어 틀리던 문항을 위해 연산 종류를 계약에 추가하고 실제로 계산한다(S6~S8). S9는 뺀다.
- 예상 성능 향상: 수치 정확도 32/66 → 약 41~44/66 (01-inspection ③묶음 14개 중 연산만 없던 12개 + 거절 누락 2개가 대상; 기간 표현을 못 읽는 3개는 실패 가능). 거절 18/20 → 20/20. 그래프가 계약에 있는 답 0/53 → 53/53 이상. op AVG·SUM·PAVG·SHR·VSA·MON 0/15 → 약 10/15. fallback 기록 0/17 → 17/17.
- 실질 반영 이점: T1-25가 고도화 대상으로 넘긴 연산을 처리해 `op=AVG 0/3 → 3/3` 같은 전→후 수치가 리포트에 남는다. 그래프가 계약에 들어가 종합 단계의 `make_chart` 툴이 바로 재사용한다.
- 비용·리스크: 1.5~2일(사람 확인 3번: 1묶음 뒤, 2묶음 뒤, 측정). 계산 로직이 늘어 기존 40문항이 바뀔 위험 → T1-24 회귀 게이트(`eval/regress.py`) 회귀 0을 완료 조건으로 둔다.

## Option C — B + 두 대상×두 시점 분석 + 데이터 모델 통합 (S1~S11 + 리팩토링 E-1)
- 접근: B에 더해 질문 분석이 "서울과 경기의 격차가 2015년보다 2025년에 얼마나"를 읽게 하고(S9), `kosis_chat/data/schema.py`의 dataclass를 `kosis_ai.schemas.Cell`로 합친다.

## Decision
옵션 B (2026-10-26 17:45, 사용자 선택). 확인 3번: 1묶음(S11, S1~S4, S10) 뒤 / 2묶음(S5~S8) 뒤 / 측정.
우선순위(사용자): 실수 최소화, 확장성. 코드 실행·평가는 사용자 PC에서 한다.

계획과 달리 구현하면서 정한 것 (1묶음):
- `schema_version` 필드 대신 `numbers_origin=None`을 "v2 이전 기록"으로 쓴다(필드 하나 덜고 같은 구분).
- fact id 규칙은 `f숫자`가 아니라 "파이썬 식별자"다. 골든 aux fact가 `a1`…을 쓰고, `derivation` 파서가 식별자를 전제한다.
- `default_applied` 키 목록은 고정하지 않는다(`period`, `가정별` 등 표마다 다름). 빈 키·빈 값만 막는다.
- `round` 상한은 10 (비율 계산 fact가 6을 넘길 수 있음).
- `answer/chart.py`가 표시 문자열을 만들려고 가짜 `Fact(source_ref="chart")`를 쓰던 것을 `render.format_number`로 바꿨다(S2의 `source_ref` 모양 규칙에 걸림).
- 예비 챗봇 답의 `usage`는 분석 호출과 챗봇 호출의 토큰 수를 더해 기록한다(이전엔 챗봇 호출만).
- 템플릿 대체 문장도 `verify()`를 거쳐 `numbers_verified`를 정한다(문제가 있으면 `decision_metadata.template_problems`).
- 저장된 실행 결과를 새 계약으로 다시 읽는 도구 `eval/recheck_contract.py`를 추가했다(확인 1에서 씀).

계획과 달리 구현하면서 정한 것 (2묶음):
- 연산(`Op`)은 `avg`·`sum`·`pavg`·`psum`·`vsa`·`shr` 여섯 개다. T1-25의 MON은 연산이 아니라 기간 표현(상반기·분기 → 월 묶음)이라 `sum`/`psum`으로 풀리고, PRD·REF-04도 기간 표현(년대, N년 전, 작년 대비)으로 풀린다. GAP·GRW는 S9(두 대상×두 시점)라 이번에 없다.
- `CalcRequest`에 `op`와 `terms`(각 term = 한 시계열의 셀 묶음 + `agg` 또는 `total`)를 두고, 연산마다 term 수·모양을 `_shape`가 검사한다. 기존 `cells`·`total` 등과 같이 쓰면 거부.
- `StatQuery`에 `op`·`period_groups`를 기록한다(`period_groups`의 시점은 모두 `periods` 안에 있어야 함).
- `Chart(kind, spec, fact_ids)`는 `StatAnswer.chart`에 들어가고, answered + `numbers_origin="code"`일 때만 허용, `fact_ids`는 `result`에 있어야 한다. `Answer.chart`(dict)는 view_run 호환으로 `chart.spec`을 그대로 둔다.
- 합계 연산은 저량(count_stock)·비율이면 판정 규칙(`stock_over_periods`)과 엔진(`_check_summable`) 두 곳에서 거절한다. 평균·합계인데 기간 일부가 표에 없으면 `partial_range` 규칙이 `no_period`로 거절한다(추이는 종전처럼 참고 문장만).
- 템플릿·그래프·엔진의 기간 문구는 `render.span_text` 하나로 쓴다(상반기·하반기·N분기는 이름으로, 월 묶음은 "1월~6월").
- `verify()`는 사실의 월 시점 숫자(6월, 2분기)를 문장에 허용한다. 채점기(`eval/grade.py`)는 아직 연·월 숫자를 허용하지 않아 월 표 답은 `unsupported_claim`이 될 수 있다 → 팀 결정 필요(아래).
