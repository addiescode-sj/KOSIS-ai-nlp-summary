# T1-27 실전 2에서 실전 1 모듈 그대로 쓰기 (작업 루트 분리 + summarize_stat)

## Goal
- 완료 기준: 실전 2 레포(`KOSIS-ai-RAG`)에서 `vendor/phase1`의 실전 1 파이프라인을 import해 돌렸을 때, 같은 골든·데이터·설정으로 **실전 1과 같은 성능**이 나온다(90문항 PASS 86/90, 문항별 판정 일치). 다르면 원인을 기록한다. 표 ID 하나로 부르는 `summarize_stat(question, table_id) -> StatAnswer`가 있어 이후 RAG 검색 결과(`TableCandidate.key`)를 바로 넘길 수 있다.
- Baseline: 실전 1 PC 레포 실행 `eval/results/20261028-144401-610979-t0-04-merge` = PASS 86/90 (비PASS: EDG-09, EDG-16·17·21). 코드 = Phase 1 master 3d08a86(#17, 49e9dda와 트리 동일).
- 범위 밖: RAG 검색 결합, DB 저장, 여러 표 결합(S7), Docker(P2-05).

## 현재 상태 (코드 확인, 3d08a86)
1. **작업 루트가 코드 위치에 고정**: `kosis_chat/config.py` `PROJECT_ROOT = Path(__file__).parents[1]` → `resolve_path`(13곳)·`load_env`가 모두 `vendor/phase1/` 기준. 골든 문항의 표 경로(`data/values/*.parquet`), `.env`, `eval/results`, `data/cache/judge.jsonl`, `docs/reports/eval-history.md`가 전부 submodule 안을 가리킨다. `eval/golden.py:68`은 따로 `ROOT / p`, `src/kosis_ai/normalize.py:20` `DATA_DIR`도 코드 기준.
2. 실전 2 팀 코드(`src/kosis_rag/metadata.py`)는 **실전 2 루트의 `data/`**를 본다 → 지금 그대로면 데이터 위치가 둘로 갈린다.
3. **`summarize_stat` 함수가 없다** (CLAUDE.md·TASK.md T1-11·schemas.py 문서에만 있음). 실제 호출: `load_table(parquet 경로)` → `StatPipeline(table, org_id=...)` → `.ask(question)` → `Answer.stat_answer`. 파일 경로를 받으므로 표 ID → 경로 연결이 없다.
4. 이미 좋은 점: `StatPipeline`은 표 로딩과 답변이 분리돼 있어(표 객체를 받음) 데이터 출처가 바뀌어도 그대로 쓸 수 있다. `fetch_table`·`normalize`는 이미 `data_dir` 인자를 받는다.

## Idea
1. 경로를 두 종류로 나눈다. **코드 루트**(`PROJECT_ROOT`: configs, 소스 스냅샷, 채점기 파일)는 그대로 두고, **작업 루트**(데이터·골든·결과·.env·로그·캐시)는 환경변수로 바꿀 수 있게 한다. 값이 없으면 지금과 똑같다 → 실전 1 사용자에게 영향 없음.
2. `summarize_stat`를 실전 1에 추가한다. 표 ID(`"101_DT_1B8000H"` = `TableInfo.key` = `TableCandidate.key`) → `data/tables.csv`의 `parquet` 칸 → `load_table` → `StatPipeline`(표별 캐시) → `ask` → `StatAnswer`.
3. 실전 2에서 `KOSIS_WORKSPACE=<실전 2 루트>`로 실전 1 `run_eval`을 그대로 돌려 baseline과 비교한다.

- 접근: A에 더해 실전 2에 `scripts/phase1_baseline.py`를 둔다. 골든 문항마다 표 경로 → 표 ID로 바꿔 `summarize_stat`만으로 답을 만들고, `grade_run`이 읽는 결과 형식으로 저장 → 같은 채점기로 채점.
