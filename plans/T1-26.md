# T1-26 자연어 품질 자동 평가 (LLM-as-a-judge)

## Goal
- 완료 기준 (TASK.md 그대로): 답변 문장의 자연어 품질을 0~2점과 문제 유형으로 자동 채점하는 단계를 하네스에 추가한다. 숫자 정확성은 기존 채점기가 보므로 judge는 문장만 본다. 사람이 판정한 사례(10/26 Notion: 환각 보정, HCX-007 vs 파이프라인)로 검출률을 재고, T1-21 사람 점수가 나오면 일치도를 잰다
- Baseline: **자연어 품질 자동 지표 없음**. 리뷰 양식(`eval/review.py`)에도 품질 칸이 없다(T1-21 예정).
  사람 판정 기록은 Notion 두 페이지(10/26)뿐이다.

이 표를 `eval/quality_labels.jsonl`(문항 id·실행·문제 유형·출처, 데이터 값 없음 → 커밋)로 남겨 검출률 측정에 쓴다.
출처가 "사람"인 행과 "Claude 후보"인 행을 구분해, 사람 행만 지표에 넣고 후보 행은 T1-21에서 확인한다.

## Idea
위치: `run_eval → grade_run → judge(새 단계, 선택) → view_run → regress`. 결과는 `<run>/grades/<최신>/quality.jsonl`과 리포트 행.
judge 입력: 질문, 최종 답변 문장(`stat_answer.text` 또는 텍스트 답), 코드가 검증한 사실 목록, 문항 종류. **숫자가 맞는지는 묻지 않는다**(기존 채점기 몫).
점수(답한 문항): 2 = 바로 답하고 읽기 쉽다 / 1 = 답은 되지만 어색하거나 장황 / 0 = 질문(일부 포함)에 답하지 않거나 오해를 부른다.
점수(거절·되묻기 문항, 별도 기준): 2 = 왜 답할 수 없는지와 표로 확인 가능한 범위를 분명히 말한다 / 1 = 사유는 있으나 어색하거나 불충분 / 0 = 사유가 없거나 틀린 사유로 오해를 부른다. 정상적인 거절이 "답하지 않음"으로 0점이 되지 않게 한다.
문제 유형 태그를 함께 낸다.
judge 모델: 파이프라인 답을 쓴 HCX-DASH-002와 다른 **HCX-007**, temperature 0. 단 10/26 비교 실행의 AI 단독 답은 HCX-007이 썼으므로, AI 단독 vs 파이프라인 비교에서는 AI 단독 쪽에 자기 선호가 생길 수 있다 → 리포트에 경고를 적고, judge 지표의 주 용도는 **파이프라인 전→후 비교**로 둔다(사용 가능한 키가 HCX뿐이라 제3 모델은 없음). HCX-007은 10/26 실행에서 90문항 1,370초·최대 113초·429 실패 1건 → 문항 간격(interval)과 재시도, 캐시로 대응하고 호출 실패 문항은 점수 없음으로 둔다. 같은 답은 캐시(답 해시 + 루브릭 버전 + 모델)해 재현·비용을 맞춘다. 비결정적이므로 회귀 게이트 판정에는 넣지 않고 별도 지표로만 둔다.

## Option A — LLM judge 하나로 전부
- 접근: 위 루브릭으로 HCX-007이 문항마다 점수와 태그를 낸다. `eval/judge.py` + 프롬프트 + 리포트 행(품질 평균, 0점 문항, 태그별 건수). pytest는 mock 클라이언트로 파싱·캐시·집계만.
- 예상 성능 향상: 자연어 품질 지표 없음 → 0~2점 자동 측정. 사람 판정 행(7건, 모두 의미·어색함 유형) 검출 추정 5~6/7. 표기 후보(약 20건)는 LLM이 일부만 잡을 것으로 추정(숫자·단위가 섞인 표기 오류는 LLM이 지나치기 쉬움).
- 실질 반영 이점: 평가 기준 "응답 품질"을 처음 자동으로 잰다. T1-21 사람 판정의 1차 분류기.
- 비용·리스크: 반나절. 실행당 HCX-007 호출 약 60~90회(10/26 실행에서 429 재시도 있었음 → interval 필요). 표기 오류 같은 기계적 문제까지 LLM에 맡겨 흔들린다.

## Option B — 코드 표기 검사 + LLM judge (의미만)
- 접근: 기계적으로 정의되는 문제는 **코드가 결정적으로** 잡는다. 리뷰에서 정상 문장 오탐을 확인해 규칙을 좁혔다: 단위 중복(`명/㎢ 명/㎢`), 연월 코드 노출(`202412년`·`202512년`), 숫자+단위 뒤 조사 불일치(단위 끝 글자의 받침으로 판정: `가구과`는 오류, `명과`·`년과`는 정상), 내부 라벨(`_계`), 미완성 조사 템플릿(`와(과)`·`은(는)`). **뺀 규칙**: 괄호 라벨(정상 괄호 27건과 구분 불가), 비율 지표의 `년`(정상 "기대수명 83.7년"과 정규식으로 구분 불가 → judge와 T1-14 단위 메타 수정에 맡김). judge는 코드가 못 보는 것만 본다: 질문 일부 무시, 근거 없는 평가, 정보 부족, 어색한 표현. 최종 점수 = judge 점수, 단 코드 검사에 걸리면 최대 1점.
- 예상 성능 향상: 사람 판정 행(7건, 모두 의미 유형) 검출은 A와 같음(추정 5~6/7) — 규칙은 사람 행에 기여하지 않는다. 차이는 표기 후보(약 20건)에서 나온다: 규칙 대상인 단위 중복·연월 코드·조사·`_계`·템플릿 약 18건을 결정적으로 검출(사람 확인 후 확정).
- 실질 반영 이점: 표기 검사는 LLM 없이 돌아 **회귀 게이트에 넣을 수 있다**. 표기 오류의 원인은 compose·템플릿 코드 버그라 고치는 일은 T1-14 몫이고, 이 검사는 고친 뒤 다시 생기지 않게 막는 장치다. LLM 호출 수는 A와 같지만 판단 범위가 좁아져 흔들림이 줄어든다.
- 비용·리스크: 하루 이내(10/28 마감 안). 규칙이 오탐할 수 있음(예: "1인 가구"의 정상 표현) → 규칙마다 pytest로 정상 문장 예시를 함께 둔다.

## Option C — 쌍 비교 judge (AI 단독 vs 파이프라인)
- 접근: 같은 문항의 두 답을 나란히 보여 주고 어느 쪽이 더 나은지 묻는다. 순서를 바꿔 두 번 물어 위치 편향을 상쇄하고, 두 번 다 같은 쪽이면 승으로 센다.
- 예상 성능 향상: "파이프라인이 AI 단독보다 자연어 품질에서 몇 승 몇 패" 한 줄. 절대 점수는 없다.
- 실질 반영 이점: Notion 비교 작업을 자동화한다. 발표용 비교 근거.
- 비용·리스크: 호출 2배(문항당 2회). 절대 점수가 없어 T1-21 0~2점과 일치도를 잴 수 없고, 파이프라인 단독 개선(전→후)도 못 잰다.

## Recommendation
**옵션 B**. 사람이 직접 찾은 문제(의미 유형)에서는 A와 같지만, 비교 HTML의 파이프라인 답에는 단위 중복·연월 코드·조사·내부 라벨 같은 표기 오류가 약 18건 더 있다. 이건 규칙으로 정의되므로 코드가 결정적으로 잡는 편이 정확하고, 회귀 게이트에 넣어 T1-14 수정 이후 다시 생기지 않게 막을 수 있다. LLM은 규칙으로 못 보는 의미 문제에만 쓴다. C의 쌍 비교는 AI 단독 답을 쓴 HCX-007이 채점하면 자기 선호가 생겨 지금 조건에서 신뢰하기 어렵다.

- 결론: judge는 "물은 것을 답했는가"와 "근거 없는 평가"는 잘 보고, 문체·라벨 어색함은 약하다. 표기 문제는 코드 검사가 결정적으로 잡는다. 사람 점수를 대신하려면 T1-21 점수로 일치도를 재야 한다(라벨 6건에 맞춰 루브릭을 더 고치면 과적합).
