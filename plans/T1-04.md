# T1-04 평가 하네스 v1 — 골든셋 Parquet 전환 + Pydantic 자동채점

## Goal
- 완료 기준 (TASK.md 그대로): 수치 정확도 %, 거절률 %, 숫자 오류 건수, 유형별 분해, 리포트 저장 → `eval/harness.py`
- 사용자 요청 (2026-10-23): 골든셋이 `data/cache/*.json`(B0 캐시)을 보도록 짜여 있다. 이를 전처리된 Parquet(`data/values/*.parquet` + `data/tables.csv`)을 로드해 채점하도록 바꾸고, Pydantic 기반 자동채점까지 염두에 두고 리팩토링한다.
- Baseline: `eval/reports/` 없음 → **baseline 없음**. 현재 상태를 수치로 적으면 다음과 같다.
  - 골든 문항이 Parquet을 가리킴: 0/40 (40문항 모두 `table: data/cache/...json` + `table_sha256`)
  - 자동 판정 가능 문항: 0/40 (판정 전부 사람이 `review.csv`로 함)
  - 골든 문항을 Pydantic으로 검증: fact만 됨 (T0-03), 문항 자체 모델 없음 (`REQUIRED_ITEM_KEYS` 문자열 검사만)
- 선행: T0-03 `[x]`. T1-03 `[ ]`이지만 골든셋 40문항(`eval/golden/stat_golden.jsonl`)은 이미 있다. 이번 태스크는 문항을 늘리지 않고 형식만 바꾼다.

## Idea
현재 흐름: `run_eval.load_golden` (dict와 키 검사) → `table` 경로의 캐시 JSON sha256 대조 → `load_table(json)` → LLM 자유 텍스트 → 사람 판정 → `scorer`.

확인한 사실:
- `kosis_chat/data/loader.py`의 `load_table`은 이미 `.parquet`을 읽는다 (format C, 메타는 `tables.csv`). 로더는 새로 만들 필요가 없다.
- 골든 셀 fact 67개는 Parquet 행과 `source_ref`·값이 모두 맞는다 (T0-03 결과 67/67). 정답 자체는 이미 Parquet 기준이다.
- 표 단위가 다르다. 캐시 6개는 Parquet 5개에 대응한다. **DT_1JC1502**는 Parquet이 158,985행이고 캐시 두 개는 그 일부다.
  - `c35fdfd8da`: 1,806행, 행정구역 코드 21개
  - `6827bccc6d`: 944행, 세종 읍면동 코드 35개

  Parquet 전체를 LLM에 넣으면 입력 한도를 넘는다. 그래서 문항이 표의 어느 범위를 보는지(`scope`)를 골든에 적어야 한다.
- 정답 비교에 필요한 계약(`StatAnswer`, `Fact`, `Refusal`)은 T0-03에서 이미 고정했다. 자동채점은 이 출력과 골든을 비교하는 규칙만 있으면 된다.

순서:
1. 골든 형식을 바꾼다. `table` + `table_sha256`을 `table_key`(예: `101_DT_1B8000H`, `tables.csv`의 key) + 선택 필드 `scope`(예: `{"dim1_code": [...]}`)로 교체한다. 변환 스크립트로 한 번 바꾸고 원본은 백업한다. `scope`는 기존 캐시의 코드 목록에서 뽑아, 바꾸기 전과 같은 셀 집합임을 확인한다.
2. 문항을 Pydantic 모델로 정의한다 (`eval/golden.py`의 `GoldenItem`). 필드는 `kind`·`type`·`allowed_reasons`·`required_facts: list[Fact]` 등이고, 모두 `kosis_ai.schemas` 상수와 타입을 재사용한다. kind별 필수 조건도 넣는다 (예: not_answerable이면 `allowed_reasons`가 있어야 함). 로드할 때 `table_key → TableInfo → parquet`으로 해석하고, 정답 fact를 Parquet 셀과 대조한다. 어긋나면 실행 전에 실패시킨다. 재현성은 manifest에 Parquet 파일 sha256을 기록해 지킨다.
3. `run_eval`을 바꾼다. 표를 `load_table(parquet)` + `scope` 필터로 읽는다. `scorer.KINDS`는 `schemas.QUESTION_KINDS`를 import한다 (T0-03 후속 항목).
4. (옵션에 따라) 자동채점, 지표, 리포트.

## Option A — 최소안: 골든 → Parquet 전환만
- 접근: 위 1~3단계만 한다. 판정은 지금처럼 사람(`review.csv`)이 하고, 자동채점은 다음 태스크로 넘긴다.
- 예상 성능 향상: Parquet 참조 문항 0/40 → 40/40. 실행 전 골든-데이터 정합성 자동 확인 0/67 → 67/67 fact. 수치 정확도 같은 하네스 지표는 그대로다 (근거: 판정 방식이 바뀌지 않음).
- 실질 반영 이점: 데이터 정확성이 오른다 (정답과 모델 입력이 같은 Parquet에서 나옴, 캐시 JSON 의존 제거). 실전 2 검색 골든도 같은 `table_key`를 쓸 수 있다.
- 비용·리스크: 약 2~3시간. 리스크는 낮다. TASK 완료 기준(지표·리포트)을 채우지 못하므로 T1-04는 `[x]`가 되지 않는다.

## Option B — 균형안: A + 결정적 자동채점기 (StatAnswer ↔ GoldenItem)
- 접근: A에 더해 `eval/grade.py`의 `grade(item: GoldenItem, answer: StatAnswer) -> Grade`를 만든다. 규칙은 코드로만 정하고 LLM은 쓰지 않는다.
  - 셀 fact 매칭: `source_ref`가 같은 fact를 찾고, 값은 Parquet 원값과 같아야 한다.
  - 계산 fact 매칭: fact id(f1·f2)와 식 문자열은 답마다 달라서 매칭 키로 쓸 수 없다. 대신 계산에 들어간 셀 fact들의 **`source_ref` 집합**으로 짝을 짓는다. 값은 골든 `round` 자릿수의 반 단위(0.5×10^-round)를 허용오차로 비교한다.
  - 필수 fact 누락·불일치 (FAIL 쪽 오류): 같은 셀이 있는데 값이 다르면 `wrong_value`, 단위가 다르면 `wrong_unit`이다. 셀이 없을 때는 `source_ref`를 분해해서, 기간만 다른 셀을 냈으면 `wrong_period`, 그 밖은 `wrong_dims`로 본다. `missing_aux`는 **aux_facts 전용**(PARTIAL)이다.
  - 숫자 오류 건수 (`unsupported_claim`): (a) TextPart 안의 숫자(V4와 같은 정규식), (b) `source_ref`가 Parquet 셀 값과 다른 셀 fact, (c) 입력 셀로 다시 계산한 값과 다른 계산 fact. 골든에 없더라도 Parquet에 근거가 있는 fact는 오류로 세지 않는다.
  - 거절 (not_answerable): 정본은 `allowed_reasons`다 (`refusal_reason`은 대표값이라 `allowed_reasons`에 포함되는지만 로드 시 검사). 답을 해 버렸으면 `missed_refusal`, 사유가 목록 밖이면 `wrong_reason`이다. answerable 문항을 거절하면 `false_refusal`이다.
  - 되묻기 (clarify): `outcome != "clarify"`면 `assumed_condition`이다.
  - 기본값 (default_allowed): `default_applied`가 비어 있으면 `unstated_default`, 키가 골든과 다르면 `disallowed_default`다.
  - 출처: `source`가 없으면 `no_source`다.
  - 자동으로 판정할 수 없는 항목: `insufficient_reason`(거절 문구의 충분성), `missing_clarification`(선택지 품질). 이 둘은 사람 판정으로 남기고 `Grade.needs_review`에 표시한다.
  - 최종 판정은 기존 `decide_verdict(kind, error_types)`를 그대로 쓴다. 사람 판정과 같은 규칙표를 공유하므로 둘을 바로 비교할 수 있다.

  `eval/harness.py --suite stat`가 결과를 집계한다 (수치 정확도 %, 거절률 %, 숫자 오류 건수, kind·type별 분해). 리포트는 `eval/reports/<날짜>-<stage>.json`/`.md`로 저장한다. B0(자유 텍스트) 실행은 지금처럼 사람 판정으로 둔다. `summarize_stat`이 나오면(T1-11) 자동 경로를 탄다.
- 예상 성능 향상: 측정 가능한 것만 적는다.
  - 오류 주입 픽스처 정답률 → 100% 목표. 골든 40문항마다 정답 StatAnswer 1개 + 오류 유형별 변형(값·기간·차원·사유·누락·텍스트 숫자)을 만들고, 기대한 error_type과 판정이 나오는지 센다.
  - 자동-사람 판정 일치율은 실제 StatAnswer가 나오는 T1-12에서 처음 측정한다. 지금은 **추정하지 않는다.**
  - 판정 소요 시간은 측정한 적이 없으므로 쓰지 않는다.
- 실질 반영 이점: 데이터 정확성·예외 처리·결과 검증 항목이 오른다. T1-12~T1-14 개선 루프에서 "몇 → 몇"을 바로 뽑을 수 있다. 실전 2·종합 하네스가 같은 `grade`/리포트 구조를 확장한다. 개인 담당(⭐) 성과 수치로 남는다.
- 비용·리스크: 약 1일, 마감 10/24 안이다. LLM 비용은 없다. 리스크는 둘이다. ① 계산 fact(증감률 등)의 매칭 규칙이 실제 파이프라인 출력과 어긋날 수 있다. `source_ref`와 `derivation`의 입력 fact 집합으로 매칭해 줄인다. ② B0 텍스트 답은 자동채점이 안 된다. 이건 범위 밖으로 명시한다.

## Option C — 고성능안: B + 텍스트 답 LLM 채점 + 정답값 Parquet 실시간 산출
- 접근: B에 더해 두 가지를 한다.
  - ① 골든에는 `source_ref`·`derivation`만 두고, 정답 숫자는 채점할 때 Parquet에서 계산한다 (정답 하드코딩 제거).
  - ② 자유 텍스트 답(B0 등)은 LLM judge가 숫자·거절 사유를 구조화(`StatAnswer` 일부)로 뽑게 하고, 같은 `grade`로 채점한다.
- 예상 성능 향상: B0 실행도 자동 판정 0/22 → 22/22. 데이터가 갱신돼도 골든 수정 0건. 다만 judge 오판으로 자동-사람 일치율이 B보다 낮아질 수 있다 (추정 85~95%, 근거 없음, 파일럿 필요).
- 실질 반영 이점: B0 베이스라인까지 자동 비교가 된다.
- 비용·리스크: 약 2일 + judge 호출 비용(문항당 1회). "LLM이 만든 숫자는 버그" 원칙과 부딪힌다 (judge가 숫자를 옮겨 적음). judge를 검증할 사람 라벨이 따로 필요하다. 10/24 마감을 넘길 가능성이 높다.

## Recommendation
**옵션 B.** 사용자 요청(Parquet 채점 + Pydantic 자동채점)과 TASK 완료 기준(지표·리포트)을 둘 다 마감 안에 채운다. 판정 규칙은 기존 `RULES`/`decide_verdict`를 그대로 써서 사람 판정과 바로 비교된다. C의 텍스트 judge는 원칙과 충돌하고 비용·검증 부담이 커서 뺀다. 정답값 실시간 산출은 B의 로드 시점 Parquet 대조로 사실상 같은 안전을 얻는다.
