## Idea
- **출처**: 제공 Parquet(`data/values/<org>_<tbl>.parquet`, 2,364표)만. KOSIS OpenAPI 클라이언트는 없고(T0-02 미완료) 보안 서약상 제공 데이터 범위 안에서 답하므로 이 태스크에 넣지 않는다.
- **위치**: `src/kosis_ai/normalize.py`. `fetch_table(table_id, filters) -> DataFrame` — Parquet 원본 칼럼 그대로 + 파생 칼럼. 원본(`value_raw`, `unit` 등)은 바꾸지 않는다. compute가 그대로 받는다.
- **필터**: `{"item": ..., "<분류 이름>": 라벨 또는 코드, "periods": [...], "start"/"end": ...}`. 시점·항목 코드는 pyarrow 읽기 단계에서 걸러 큰 표도 1~2초.
  분류 라벨 해석(같은 라벨이 여러 수준이면 최상위 코드)은 compute `select`의 규칙을 그대로 쓴다 — 규칙은 한 곳.
- **팀원 코드와의 관계**: B0(`kosis_chat`)는 표를 LLM에 넣는 경로이고, 실전 1(`kosis_ai`)은 코드가 계산하는 경로다. 팀원 `scope.py`는 LLM에 넣을 범위를 자르고, `fetch_table`은 계산할 셀을 고른다.
  - 단위 규칙이 세 곳(B0 `infer_unit`, 스키마 `unit_or_suffix`, compute `UNIT_OVERRIDES`)에 있다 → `kosis_ai.normalize.resolve_unit` 하나로 모으고 compute·스키마가 쓴다.
    B0 로더가 이 함수를 쓰게 바꾸는 것은 팀원 영역이라 이번에는 하지 않고, 공유 문서로 제안한다.
  - 팀원 `scope.same_level`은 `00`(전국)·`03`(동부)·`11`(서울)을 같은 수준으로 본다. 범위 자르기에는 맞지만 그 범위를 더하면 2배 합산(EDA 2-2)이 된다. compute는 시도 이름 표로 피하고 있다 — 공유 문서에 적는다.
- **공통 처리 (모든 옵션)**:
  - **단위** `unit_resolved`, `unit_source` — 리뷰 반영 순서:
    ① `unit` 칼럼(허용 목록에 있을 때만, 가짜 단위는 버림) ② 항목명·분류 라벨 괄호(허용 목록, EDA 2-4) ③ 보정표(`합계출산율→명`, `기대수명→년`)
    ④ 메타 단위 — **그 표의 다른 행에 다른 단위가 없고, 항목이 비율·평균·지수(`율`·`비`·`평균`·`지수`)가 아닐 때만** ⑤ `None`(단위 미상).
    `dimUnitYn`은 2,364표 모두 `N`이라 판단 근거로 쓰지 않는다.
  - **기호**: `value_kind`(7종)를 그대로 쓰고 새 enum을 만들지 않는다. LLM·답변용 문구 사전 `VALUE_LABELS`만 둔다
    (`dash`→해당 없음, `x_secret`·`asterisk`→비공개, `blank`→그 시점에 집계 안 함, `ellipsis`→자료 없음, `other_text`→해석 불가). `-`를 0으로 바꾸지 않는다는 테스트를 남긴다.
  - **키 중복**: 조회 결과에 같은 키가 둘 이상이면 값을 돌려주지 않고 `ComputeError("class_mismatch", "표에 이름 없는 분류가 숨어 있어 칸을 구분할 수 없습니다")`.
    `class_mismatch`는 "질문 조건으로 칸을 특정할 수 없음"이라 기존 사유로 맞고, 스키마를 바꾸지 않는다.
- 순서: 조회+필터 → 단위 → 기호 문구 → 키 중복 → (옵션에 따라) measure_kind·R8 / 숨은 분류 복원 → compute 연결 → 측정.

## Option A — 조회 + 단위·기호·키 중복 (최소)
- 접근: 위 "공통 처리"만. compute의 `_unit`·`UNIT_OVERRIDES`를 `resolve_unit`으로 바꾼다.
- 예상 성능 향상: M1 24 → 약 260표 해결, 틀리게 붙는 표 0 (근거: 메타 무조건 351에서 리뷰 실측 오류 82표 이상을 조건으로 걸러낸 상한 ≈ 269; 실측으로 확정).
  M2 0/69 → 69/69. M3 31 → 0. M4 5/7 그대로. M5 유지. M6 2초 이하.
- 실질 반영 이점: 데이터 정확성·예외 처리. 단위 규칙이 한 곳으로. 숨은 분류 표의 섞인 값이 계산에 들어가지 않는다.
- 비용·리스크: 3시간. 마감 10/23(오늘)은 전제 3개 때문에 넘길 수 있다. R8은 남는다.

## Option B — A + `measure_kind` 칼럼 + compute R8
- 접근: A에 `measure_kind`(스키마 `MeasureKind`) 칼럼을 더한다. 단위·항목명 키워드 규칙(`%`·`…당`·`명/㎢`·`배`·`율`·`비` → ratio, `평균`·`중위` → average, `지수` → index,
  `인구`·`가구`·`세대` → count_stock, `건수`·`출생`·`사망`·`이동`·`혼인`·`이혼` → count_flow) + 수동 지정표로 덮어씀.
  compute에는 **R8 검사만** 추가한다(ratio·average·index 합산 금지, count_stock 시점 간 합산 금지). compute의 total·비교 대상 판정(T1-07 검증 완료)은 건드리지 않는다 — 리뷰 반영.
- 예상 성능 향상: A의 수치 + M4 5/7 → 7/7 (근거: 남은 2건이 `measure_kind`만 기다림), S-REF-06을 compute가 `not_aggregatable`로 거절.
  `measure_kind` 분포를 2,364표에 돌려 Result에 남긴다(키워드 미분류 표 수 = 수동 지정표 후보).
- 실질 반영 이점: 데이터 정확성. T1-08이 비율 합산 규칙을 따로 만들지 않아도 된다.
- 비용·리스크: 4시간. 키워드 규칙이 골든 6개 표 밖에서 틀릴 수 있다 → 미분류는 `None`으로 두고 R8은 `None`이면 합산을 허용하지 않는다(보수적).

## Option C — B + ZIP 숨은 분류 복원
- 접근: B에 더해 키 중복 31표의 숨은 상위 분류를 **Parquet 행 순서**로 복원한다. 리뷰 실측: 행 순서에 `계/남/여` 묶음이 그대로 남아 있다(예: 3,778,098 = 2,594,852 + 1,183,246).
  `X-계`·`X_계` 항목이 나오면 새 묶음을 시작하는 EDA 2-6 규칙으로 `dim_hidden` 칼럼을 만든다.
- 예상 성능 향상: M3가 "차단 31"이 아니라 "정상 조회 31". 골든 지표는 B와 같다(골든에 31표 없음).
- 실질 반영 이점: 2,364표 전체를 조회 가능.
- 비용·리스크: 1일. 데이터 빌드(`build_parquet.py`, `map_zip_item_ids.py`)는 팀원 영역이고 행 순서 의존이 데이터 재빌드에 약하다 → 빌드 단계에서 고치는 것이 맞아 팀원과 합의가 먼저다.
