# T1-24 골든셋 회귀 테스트 게이트

## Goal
- 완료 기준 (TASK.md 그대로): `run_eval → grade_run → view_run → regress`으로 위치를 고정한다. T1-20 결과를 기준선으로 두고, 이후 모든 수정마다 문항별 전환(정답→오답 = Regression, 오답→정답 = Improvement)·평가 조건 일치·회귀 원인 단계를 리포트하며, 회귀가 1건이라도 있으면 실패로 끝난다
- Baseline: 회귀 검출 수단 없음. 지금은 `grade_run`이 실행 하나의 합계(PASS 수·수치 정확도)만 낸다.
  전후 비교는 사람이 두 `report.md`를 눈으로 비교해야 하고, "합계는 올랐는데 기존 정답이 깨진" 경우를 놓친다.
  가장 최근 C 실행: `eval/results/20261025-120211-701208-C-stat-chart` (40문항, HCX-DASH-002, oracle, wide)

## Idea
회귀 테스트 자료(동일 골든셋 → v1.0 평가 → 기준선 저장 → 수정 → 같은 골든셋으로 재평가 → 문항별 전환 분석)를
현재 평가 흐름에 그대로 대응시킨다.

```
run_eval (답 생성) → grade_run (자동 채점, grades.jsonl) → view_run (보기) → regress (NEW: 기준선과 문항별 비교, 게이트)
                                                              ↑
                                                기준선 = T1-20에서 보존한 C 실행의 채점 결과
```

- **위치를 grade_run 뒤로 고정하는 이유**: 회귀는 "문항별 판정"끼리 비교해야 한다. 판정은 grade_run이 만들고(LLM 없음, 결정적),
  run_eval은 LLM 호출이라 비결정적이다. 채점 결과끼리 비교하면 같은 실행을 다시 비교해도 결과가 같다.
  사람 판정(review)·자연어 품질(T1-21)은 사람이 매번 할 수 없으므로 게이트에 넣지 않는다.
- **비교 규칙**: 판정 순위 PASS > PARTIAL > FAIL. 순위가 내려가면 Regression, 올라가면 Improvement.
  골든 sha256·scoring_version·채점기 파일(eval/grade.py, eval/scorer.py) sha256이 다르면 비교를 거부한다(같은 시험지·같은 채점자가 아님). 모델·temperature·프롬프트·scope·직렬화·데이터 해시가 다르면 리포트 맨 위에 경고한다.
- **회귀 원인 단계**: 새로 생긴 error_type을 구조도 단계에 대응시킨다.
  판정(1) false_refusal·missed_refusal·wrong_reason·insufficient_reason / 분석(2·2b) wrong_dims·wrong_period·assumed_condition·missing_clarification·disallowed_default·unstated_default /
  계산(3) wrong_value·wrong_unit / 문장·검증(4·5) unsupported_claim·missing_aux·no_source / 실행 run_failure.
  여기에 `results.jsonl`의 경로(route/compose: rules, model, template, fallback_chatbot) 전→후를 같이 적는다.
- **출력**: 새 실행의 `grades/<stamp>/regress.md`·`regress.json`. 2×2 전환표(자료 4쪽 표), 유형·kind별 PASS 변화, 회귀 문항 목록(전→후 판정, 새 오류, 원인 단계, 경로 변화).
  회귀 > 0이면 종료 코드 1.

## Option A — 별도 비교 스크립트 (grades 폴더 ↔ grades 폴더)
- 접근: `python -m eval.regress --base <기준 grades 폴더> --new <새 grades 폴더>`. 두 실행의 `grades.jsonl`·`manifest.json`·`results.jsonl`(경로)을 읽어 위 규칙대로 비교. 기준선은 매번 경로로 넘긴다.
- 예상 성능 향상: 모델 지표는 바뀌지 않는다(평가 도구). 측정할 것: 오류 주입 검출률 — 기준 grades에서 판정 k개를 낮춘 사본 → 회귀 k/k 검출, 자기 자신 비교 → 회귀 0 (거짓 양성 0).
  다음 단계 T1-13·T1-14 결과에 "PASS 14/25 → ? / 회귀 n건 / 원인 단계"를 함께 남길 수 있게 된다.
- 실질 반영 이점: 결과 검증·기술 설계. 개선 근거 2건마다 회귀 증거가 붙는다.
- 비용·리스크: 1~2시간, LLM 0. `eval/results/`가 gitignore라 기준 폴더가 각자 PC에만 있다 → 팀원끼리 기준선이 어긋날 수 있다. 채점기(eval/grade.py)가 바뀌면 판정 차이를 모델 회귀로 오인할 수 있다(scoring_version·채점기 해시 비교로 막음).

## Option B — 커밋되는 판정 스냅샷을 기준선으로
- 접근: A의 비교 로직을 쓰되 기준선의 저장 방식을 바꾼다. `--accept`로 기준 실행을 `eval/baselines/stat.json`에 고정: 문항별 verdict·error_types·kind·type·route/compose, 평가 조건(모델 이름·temperature·프롬프트 버전·scope·직렬화·골든/데이터 sha256·scoring_version·채점기 파일 sha256), 원본 run id.
  `Grade.details`·답변 문장·셀 값은 넣지 않는다(데이터 값 미커밋). `--base` 생략 시 이 파일과 비교. 덮어쓰기는 `--accept`를 줄 때만 하고 이전 run id를 출력.
- 예상 성능 향상: A와 같은 검출률 + 팀원 간 기준선 불일치 0 (같은 파일을 git으로 공유).
- 실질 반영 이점: A + 협업 점수. 기준선 변경 이력이 git 로그로 남아 "언제 무엇으로 기준선을 올렸나"가 발표 근거. 같은 형식(`search.json`, `agent.json`)으로 T2-03·T3-06에 재사용.
- 비용·리스크: 2~3시간. 채점기가 바뀌면 스냅샷은 다시 채점할 수 없다 → 비교를 거부하고 "기준 실행을 새 채점기로 grade_run 후 --accept" 안내(기준 results.jsonl 보유자가 1회 수행).

## Option C — grade_run --baseline: 원답을 현재 채점기로 둘 다 다시 채점
- 접근: 새 모듈 없이 `grade_run --run <새> --baseline <기준 run 폴더>`. 기준 실행의 results.jsonl을 지금의 grade()로 다시 채점해 같은 채점기로 비교 → 채점기 변경 문제가 원천적으로 없다. `--runs N` 실행이면 `--run-index`별로 채점해 다수결 판정·흔들린 문항(flaky)을 따로 표시.
- 예상 성능 향상: A의 검출률 + 채점기 변경 오인 0. 흔들림 건수는 미측정(temperature 0).
- 실질 반영 이점: 자료의 "필요하면 여러 번 실행"까지 충족. 다만 기준 results.jsonl(데이터 값 포함, gitignore)이 각자 PC에 있어야 해 팀 공유가 안 된다.
- 비용·리스크: 2~3시간(+ 반복 실행 시 HCX 호출 N배, 62×3 ≈ 15분+). grade_run이 채점·비교 두 책임을 갖게 된다.

## Recommendation
**옵션 B**. 세 옵션의 검출 로직은 같고, 차이는 "기준선을 어디에 두느냐"다. 팀 프로젝트라 기준선이 git에 있어야 4명이 같은 기준으로 회귀를 센다(A·C는 gitignore 폴더 의존).
채점기 변경은 B에서도 거부+재채점 안내로 막힌다. 흔들림(C)은 T1-20 실행을 한 번 더 돌려 B로 기준선끼리 비교해 보면 측정되므로, 회귀가 나올 때 추가한다.

### 기준선과 범위 (리뷰 반영)
- 기준선은 아직 없다: T1-20(62문항)이 미완료. 구현 검증은 기존 40문항 C 실행(`20261025-120211-701208-C-stat-chart`)으로 하고, T1-20 실행이 나오면 `--accept`로 첫 기준선을 고정한다.
- 거절 전환 강조: false_refusal·missed_refusal가 새로 생긴 문항은 리포트 상단에 따로 묶는다(데이터 정확성 > 예외 처리 원칙).
- 흐름: `grade_run → view_run → regress`. regress가 exit 1이어도 view.html은 이미 만들어져 확인할 수 있다. view.html에 회귀 표시는 넣지 않는다(regress.md로 충분, 필요하면 T1-15에서).
