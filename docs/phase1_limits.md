# 실전 1 한계·개선사항·Phase 2 이월 범위 (산출물④, T1-15)

작성 2026-10-27 · 담당 임도유 · 기준 master `4285f0c` · 계획: [plans/T1-15.md](../plans/T1-15.md)

이 문서는 실전 1(통계 수치 요약 모듈)을 마치며 무엇이 되고 무엇이 안 되는지, 다음에 무엇을 고칠지 정리한다.
멘토 질문 6개(아키텍처·스키마 필드·골든셋 분포·메트릭·실패 유형·개선 우선순위)에 차례로 답한다.

**숫자 규칙**
- 이 문서는 새 숫자를 만들지 않는다. 병합된 태스크 결과(각 plan의 `## Result`, [TASK.md](../TASK.md))와 커밋된 리포트의 숫자만 옮긴다.
- 숫자 표에는 마지막 칸에 `출처`를 단다. [tests/test_phase1_limits_doc.py](../tests/test_phase1_limits_doc.py)가 그 숫자가 출처 파일에 실제로 있는지, 문서가 가리키는 경로가 레포에 있는지 검사한다.
- 실행 조건(백엔드, 골든 문항 수)이 다른 숫자는 한 표에 섞지 않는다. 표마다 조건을 적는다.
- 아직 끝나지 않은 태스크의 결과는 숫자 대신 **미확정**으로 적고, 맨 끝 체크리스트에 모았다.

## 0. 요약

- 실전 1은 "숫자는 코드가 계산하고 모델은 문장만 쓴다"는 C 파이프라인으로 만들었다. 답할 수 없는 질문은 사유 코드와 함께 거절한다.
- 정확성과 예외 처리는 기본 골든셋에서 안정적이다. mock 90문항에서 거절률 20/20, 되묻기 3/3이다(T1-14).
- 가장 큰 약점은 **질의 이해**다. 여러 시점을 묶는 복합 질문 28문항에서 규칙 분석이 27건 중 13건 실패했고(T1-22), PASS는 1/28이다(T1-25).
- AI 단독(B0) 대비 C의 최종 비교 수치는 T1-20(62문항 고정 실행)과 T1-21(사람 판정)이 끝나야 확정된다. **미확정**

## 1. 아키텍처

```
질문 ─▶ 판정 ─┬─ 불가 → Refusal (사유 코드 + 대신 답할 수 있는 범위)
             ├─ 모호 → 되묻기 (선택지)
             └─ 가능 → 규칙 분석 → 슬롯(StatQuery)
                          └ 실패 → 모델 보완(llm_fill) → 그래도 실패 → 예비 챗봇
슬롯 ─▶ 계산 (pandas) ─▶ 근거 사실 (셀 ref 또는 계산식)
사실 ─▶ 문장 작성 (HCX) ─▶ 숫자 검증 ─┬─ 통과 → 최종 답 + 출처 + 차트
                                    └─ 실패 → 템플릿 문장으로 대체
```

| 단계 | 코드 | T1-22 span 이름 |
| --- | --- | --- |
| 판정 (거절·되묻기·기본값) | `kosis_chat/judge/answerability.py`, `kosis_chat/judge/question.py` | `judge` |
| 규칙 분석 → 슬롯 | `kosis_chat/compute/analyze.py` | `analyze.rules` |
| 모델 보완 | `kosis_chat/llm/analyze_fill.py` | `analyze.llm_fill` |
| 계산 | `kosis_chat/compute/engine.py` | `compute` |
| 문장 작성 | `kosis_chat/llm/compose.py` | `compose` |
| 숫자 검증 / 템플릿 대체 | `kosis_chat/answer/verify.py`, `kosis_chat/answer/template.py` | `verify` / `template` |
| 예비 챗봇 | `kosis_chat/chatbot.py` | `fallback_chatbot` |
| 차트 (Vega-Lite) | `kosis_chat/answer/chart.py` | — |

- 진입점은 `kosis_chat/pipeline.py`다. 원인을 묻는 부분은 수치 답 뒤에 거절 안내 문장을 붙인다(T1-14 `_causal_note`).
- 데이터는 KOSIS 2,364표를 Parquet(long 형식)으로 정규화해 쓴다. 기호 칸(`-`, `X` 등)은 숫자로 바꾸지 않고 상태로 남긴다. 근거: [docs/eda-full.md](eda-full.md)
- 평가 흐름: `run_eval → grade_run → view_run → regress`. 사람 판정은 `eval/review.py`, 문장 품질은 `eval/judge.py`가 맡는다.
- 단계마다 `{name, start_ms, duration_ms, status, attributes}` span을 남긴다. 필드는 OpenTelemetry와 1:1이라 Phase 2(T2-15)에서 그대로 옮긴다([plans/T1-22.md](../plans/T1-22.md)).

## 2. 스키마 필드

세 단계(실전 1·실전 2·종합)가 같이 쓰는 계약은 `src/kosis_ai/schemas.py`에 있다. 코드 목록(질문 유형, 문항 kind, 거절 사유, 값 상태)은 이 파일과 [docs/question_types.md](question_types.md)가 정본이라 여기에 다시 적지 않는다.

| 스키마 | 역할 | 실전 2·종합에서 |
| --- | --- | --- |
| `StatQuery` | 질문에서 뽑은 슬롯: 질문 유형, 항목, 기간, 분류 조건, 비교 대상, 순위 축, 모호한 점 | 검색 질의 해석과 슬롯 모델 비교(T2-16)에 재사용 |
| `Fact` | 근거 사실 하나: 값, 단위, 시점, 분류, 원본 셀 ref, 계산식, 반올림, 측정 종류 | 차트 데이터의 원천 |
| `Refusal` | 거절 사유 코드, 안내 문장, 대신 답할 수 있는 범위 | 검색의 "답 없음" 판정과 같은 형식 |
| `StatAnswer` | `summarize_stat`의 반환값: 결과(답·거절·되묻기), 슬롯, 근거 사실, 문장 조각, 출처 | 종합 단계 에이전트 툴의 출력 |

- 문장 조각(`parts`)은 근거 사실을 id로만 가리킨다. 연결 문장 속 숫자는 검증기가 거부한다. 모델이 쓴 숫자가 답에 들어갈 길을 구조로 막은 것이다.

| --- | --- | --- |
| 골든 fact 스키마 적합 | 0/98 → 98/98 | [TASK.md](../TASK.md) |
