# Plan: 실전 프로젝트 1 — 통계표 수치 요약 챗봇

- id: 20261020-stage1-table-summary
- status: DRAFT rev 3 (B1~B4 구현 전 확정 필요)
- date: 2026-10-20 (rev 3: 코드 작성 전 설계 수정 권고 반영)
- baseline: docs/plans/20261020-baseline-chatbot/PLAN.md (B0, 입력 자료형·채점 기준·비교 규약의 원본)
- due: 2026-10-28

## Intent

통계표 하나(Tabular Data)와 자연어 질문이 주어지면, 그 표에 실제로 있는 수치만으로
정확한 답을 단위·출처와 함께 자연어로 만드는 챗봇을 만든다. 표를 "찾는" 일은 하지 않는다
(2차 RAG의 몫). 2차·최종에서 이 모듈을 그대로 재사용하므로, 표 입력과 답변 생성을
분리된 단계로 설계하는 것이 숨은 핵심 요구다.

## Problem / Why

- LLM에 표를 통째로 넣으면 수치를 잘못 읽거나 계산을 틀리고, 없는 숫자를 만들어낸다.
- 평가 기준 중 데이터 정확성·예외 처리 비중이 크고, "검증되지 않은 수치 생성 금지"가 규칙이다.
- 10/28까지 8일이라 범위를 좁게 고정해야 한다.

## 처리 흐름

1. 입력: 통계표 데이터(KOSIS OpenAPI 응답 또는 제공 파일) + 표 메타데이터 + 질문
2. 질문 분석: 질문 유형(5종) 분류, 조건(시점·분류·항목) 추출 — HCX
3. 모호성 판정: 조건이 비거나 여러 해석이 가능하면 기본값 적용 또는 되묻기 (아래 "모호한 질문 처리")
4. 전처리: 전체 셀을 정규화 (결측·단위·계/소계 표시, 원본 보존) (PREPROCESSING.md R1~R5)
5. 계산 계획: 질문 유형에 따라 분자·분모·비교 기준 시점을 먼저 정한다
6. 행 선택: 답변 대상 행(질문 조건)과 계산 근거 행(계산 계획)을 정규화 전체 자료에서 따로 고른다 (R6)
7. 계산 가능 판정 + 계산: 합산 가능 여부·구성비 분모·결측 규칙(R8·R9)을 통과한 경우에만 코드로 계산 → facts
8. 답변 불가 판정: 필요한 행이 없거나 계산 불가면 "답변 불가 + 이유 + 가능한 범위"
9. 생성: LLM은 사용할 fact_id와 설명 구성만 고르고, 수치 문장은 fact 기반 템플릿으로 렌더링한다
10. 결합 검증: 렌더링된 수치 문장과 LLM 설명 문장을 검사 → 실패 시 1회 재생성 → 그래도 실패하면 facts 템플릿 답변. 재생성·템플릿 대체 횟수를 결과에 기록

## 결합 검증 (숫자 존재 검사를 대체)

숫자가 facts 어딘가에 "있다"는 것만으로는 부족하다. 2023년 값을 2024년이라고 말하거나, 남자 값을 전체라고 말해도 숫자 존재 검사는 통과한다.
자유 문장의 시점·분류 연결을 코드로 전부 검증하기는 어렵기 때문에, 1차에서는 **수치 문장을 템플릿으로 만들어 검증 범위를 줄인다.**

- fact = {fact_id, value, unit, period, dims, measure_kind, derivation(원본 셀 source_ref 또는 계산식 + 입력 fact_id), source_ref}
- LLM 출력(구조화): `plan` = [{kind: "fact", fact_id} | {kind: "text", text}] — 순서대로 답변을 구성
- `fact` 항목은 `llm/render.py`가 템플릿으로 문장화한다: "{period} {dims} {item}은(는) {value}{unit}입니다" (유형별 템플릿 몇 개)
- `text` 항목(연결·설명 문장)에는 **통계 수치 주장을 넣을 수 없다** (시점 표기·연령 범위는 허용)

| 검사 | 대상 | 내용 |
| --- | --- | --- |
| V1 참조 | fact 항목 | 모든 fact_id가 facts에 존재한다 |
| V2 계산 근거 | 계산 fact | derivation의 입력 fact가 모두 존재하고, 식을 다시 계산한 값이 같다 |
| V3 단위 | fact 항목 | 렌더링 단위가 fact.unit과 같다 (%와 %p 구분) |
| V4 텍스트 수치 금지 | text 항목 | 통계 수치 주장으로 보이는 숫자가 있으면 실패 |
| V5 조건 일치 | 전체 | 사용한 fact의 시점·분류가 질문 분석 조건(또는 명시한 기본값)과 같다 |

- 템플릿이 시점·분류를 직접 쓰므로, 자유 문장의 "직전 문장 상속" 같은 표현은 지원하지 않는다. 지원하지 않는 형식은 검증 성공으로 간주하지 않는다 (V4 실패로 처리).
- 핵심 수치가 질문 조건에 맞는지(올바른 fact를 골랐는지)는 검증기가 아니라 골든셋 평가로 따로 확인한다. 내부 검증 통과율과 골든셋 정답률은 별도 지표다.

## 합산 가능 여부와 구성비 분모

- 각 셀에 measure_kind를 붙인다: count_stock(시점 인구·가구 수), count_flow(출생·이동 등 기간 합계), ratio(%, 율, 성비), average(평균·중위), index.
- 합산은 count_* 이고, 단위·시점·나머지 분류가 같고, 같은 분류 수준의 말단 값이며, 결측이 없을 때만 허용한다.
- count_stock은 시점 간 합산 금지. count_flow는 기간이 빠짐없이 있을 때만 합산(예: 12개월 → 연).
- ratio·average·index는 합산·단순 평균 금지. 가중 평균은 1차 범위 밖 → "계산 불가" 사유로 처리.
- 구성비 = 부분 / 분모. 분모는 같은 표·같은 시점·같은 단위·같은 나머지 분류의 "계" 셀을 우선 쓴다.
- "계"가 없으면 그 분류의 전체 말단 범주 합을 분모로 쓰되 합산 가능 조건을 모두 만족할 때만. 질문으로 좁힌 일부 행의 합을 전체로 보지 않는다.
- 결측은 분자·사용하는 분모·합산에 필요한 말단에만 적용한다. 계산에 쓰지 않는 다른 항목의 결측으로 거부하지 않는다. 분모 0은 계산 불가 (PREPROCESSING R9).
- 답변에 분모를 함께 말한다 ("2024년 전체 인구 N명 중 …").

## 모호한 질문 처리

| 경우 | 처리 |
| --- | --- |
| 시점 없음 | 표의 최신 시점으로 답하고 "가장 최근 시점 기준"이라고 명시 |
| 분류 없음 (성별 등) | "계" 값으로 답하고 기준을 명시 |
| 기간 범위 불명 ("최근") | 최근 5개 시점으로 답하고 범위를 명시 |
| 항목이 여러 개 매칭 (예: 인구 → 총인구/내국인/외국인) | 숫자 없이 후보 2~3개를 제시하고 한 번 되묻기 |
| 비교 대상 불명 | 숫자 없이 비교 기준을 되묻기 |

원칙: 기본값으로 답해도 사용자가 오해하지 않을 때만 기본값을 쓰고, 해석에 따라 답 숫자가 달라지면 되묻는다.

## Requirements

FR-001: 입력은 베이스라인의 TableInput(셀 단위·원본 값·source_ref 보존)을 그대로 쓰고, PREPROCESSING.md의 파생 필드를 더한다.
FR-002: 질문을 5개 유형(단순 수치, 추이, 비교, 구성비, 최댓값·최솟값) 또는 "범위 밖"으로 분류한다.
FR-003: 질문에서 시점·분류·항목 조건을 추출해 표의 실제 값 목록과 매칭한다.
FR-004: 결측 표기, 단위 혼재, 계/소계 행을 규칙에 따라 처리한다.
FR-005: 유형별 계산은 코드로 수행하고 결과를 facts(값, 단위, 시점, 분류, measure_kind, derivation, 출처)로 만든다.
FR-006: 답변 불가 사유(없는 시점·항목, 분류 기준 불일치, 단위·기준 비교 불가, 합산·분모 조건 불충족, 인과·정책 판단 요구, 결측·자료 부족)를 판정한다.
FR-007: 답변은 고정 형식을 따른다: 핵심 답 1문장 → 근거 수치 → 출처(KOSIS / 조사명 / 표명) → 한계·적용한 기본값(있을 때).
FR-008: 수치 문장은 fact 기반 템플릿으로 렌더링하고, 결합 검증(V1~V5) 실패 시 재생성 1회 후 템플릿 답변으로 대체한다. 재생성·대체 횟수와 비율을 기록한다.
FR-009: 전처리는 PREPROCESSING.md를 따르며 규칙마다 테스트 케이스가 있다.
FR-010: 계산 계획(분자·분모·기준 시점)을 먼저 정하고, 답변 대상 행과 계산 근거 행을 따로 선택한 뒤 합산·분모·결측 규칙(R8·R9)을 적용한다.
FR-011: 모호한 질문은 위 표에 따라 기본값 적용(명시) 또는 되묻기로 처리한다.
FR-012: (조건부) 직렬화 형식 3종(마크다운 표 / JSON 레코드 / 문장형)을 비교한다. 단일 표 E2E 게이트(AC-009) 통과 후에만 진행한다.
NFR-001: 전처리·계산·검증은 LLM 없이 결정적으로 동작하고 단위 테스트가 가능하다.
NFR-002: 표 입력과 질문만 바꾸면 2차(RAG가 고른 표)에서 그대로 호출할 수 있는 인터페이스.
NFR-003: API 키는 .env로만 읽는다. Python 3.12.

## 골든셋과 합격 기준

문항 형식·문항 종류(답변 가능 / 답변 불가 / 되묻기 필요 / 기본값 허용)·판정(FAIL→PASS→PARTIAL)·단위별 허용오차·사람 최종 판정 절차는 **베이스라인 PLAN의 "채점 기준"을 그대로 쓴다.** 정답 facts는 코드로 원본에서 뽑고 사람이 확인한다.
아래 합격 기준은 **1차 서비스의 목표 성능**이며, B0 기준 점수(측정만 하고 합격 여부를 따지지 않음)와 별개다. 미검토 문항이 남은 잠정 점수로는 합격 판정을 하지 않는다.

| 지표 | 대상 문항 | 합격 기준 (초안) |
| --- | --- | --- |
| 답변 가능 PASS | 답변 가능 | ≥ 90% |
| 근거 없는 통계 수치 주장 | 전체 | 0건 |
| 답변 불가 PASS | 답변 불가 | ≥ 90% |
| 되묻기·기본값 PASS | 되묻기 필요 + 기본값 허용 | ≥ 80% |
| 출처 표기 | 답변한 문항 | 100% |
| 실행 실패 | 전체 | 0건 (있으면 원인 기록 후 재실행) |

구성(초안): 대상 표당 유형 5종 × 2문항 + 불가 4 + 모호 3. 단일 표 게이트는 이 1세트(약 17문항), 최종은 대상 표 전체.

## Acceptance Criteria

AC-001: 골든셋 평가(HCX 실행 → 사람 확정 판정 → 집계)가 위 지표를 docs/reports/eval-history.md에 남긴다.
AC-002: 확정(비잠정) 점수로 위 합격 기준을 모두 만족한다 (미달 항목은 원인과 개선안을 리포트에 기록).
AC-003: 결합 검증 V1~V5 각각에 대해 실패해야 하는 출력 예시가 단위 테스트에서 걸러지고, 지원하지 않는 표현은 통과로 처리되지 않는다.
AC-004: 합산 가능 여부·구성비 분모·결측 규칙의 허용/거부 사례가 단위 테스트로 있다. 일부 분류만 요청해도 분모가 공식 합계로 선택되는 테스트 포함.
AC-005: `bash scripts/verify.sh`가 네트워크·API 키 없이 pytest(저장된 결과의 오프라인 재채점 테스트 포함)를 실행하고 0으로 종료한다. 새 HCX 호출은 verify.sh에 넣지 않는다.
AC-006: 필수 산출물 4종이 docs/에 있다: 질문 유형·답변 가능/불가 기준 문서, 프로그램, 질문·정답 예시와 테스트 결과, 한계·개선사항.
AC-007: 전처리 명세의 규칙별 테스트가 verify.sh에서 통과한다.
AC-008: (조건부) 직렬화 비교 결과(형식별 결합 정확도, 답변 불가 처리율, 평균 입력 토큰)가 docs/reports/에 남는다.
AC-009: 단일 표 E2E 게이트 — 실제 통계표 1개로 입력부터 결합 검증까지 HCX로 전체 흐름이 돌고, 그 표의 골든셋 확정 점수가 합격 기준을 만족한다. HCX 미실행·잠정 점수는 게이트 미통과로 본다.

## Technical Decisions

D-001: 계산은 코드, 문장은 LLM (유지)
- Rationale: 수치 오류와 환각을 구조적으로 차단, 검증 가능
- Linked: FR-005, FR-008
- Rejected alternative: 표 전체를 프롬프트에 넣고 LLM이 계산 — 정확도·검증 불가

D-002: LLM 입력은 필터된 소형 표 + 메타 헤더 + facts, 초기 형식은 마크다운 표
- Rationale: 토큰 절약. 형식 비교는 E2E가 선 뒤에 한다(FR-012)
- Linked: FR-001, FR-004, FR-012
- Rejected alternative: 원본 JSON 그대로 — 길고 컬럼명이 코드(C1_NM 등)라 해석 오류

D-003: 질문 분석은 HCX의 구조화 출력(JSON: type, period, filters, item, ambiguity)
- Rationale: 이후 단계가 규칙 기반으로 처리 가능, 2차에서 재사용
- Linked: FR-002, FR-003, FR-011
- Rejected alternative: 키워드 규칙만 — 표현 다양성 대응 불가

D-004: 골든셋을 제공 범위(인구 분야 14개 조사)에서 새로 만든다
- Rationale: 브리프 예시(기업 통계)는 제공 데이터 밖. 예시 질문은 "범위 밖" 테스트로 사용
- Linked: AC-001, AC-002

D-005: 전처리를 PLAN과 분리된 명세 문서로 관리
- Rationale: 답변 품질의 대부분을 결정하고, 2차·최종에서도 같은 규칙을 재사용
- Linked: FR-009

D-006: 숫자 존재 검사 대신 fact 기반 템플릿 수치 문장 + 결합 검증
- Rationale: 시점·분류를 바꿔 말하는 오류는 숫자 존재 검사로 잡히지 않고, 자유 문장의 시점·분류 연결은 코드로 전부 검증하기 어렵다. 수치 문장을 템플릿으로 만들면 검증 범위가 작고 확실해진다
- Linked: FR-008, AC-003
- Rejected alternative: 자유 문장 + claims 목록 대조 — 직전 문장 상속 등 표현이 다양해 검증 누락 위험

D-007: 단일 표 E2E를 직렬화 실험보다 먼저 완성
- Rationale: 흐름 전체가 서지 않으면 형식 비교 결과를 해석할 수 없다. 일정이 밀리면 실험은 "개선사항"으로 이월
- Linked: AC-009, FR-012

## Scope

### In scope
- 전처리 명세와 규칙별 테스트
- 질문 분석, 모호성 처리, 전처리, 합산·분모 판정, 계산, 답변 불가 판정, 답변 생성, 결합 검증 모듈
- 골든셋, 합격 기준, 자동 평가 스크립트, verify.sh 연결
- 간단한 실행 인터페이스(CLI 또는 노트북)
- 필수 산출 문서 4종
- (조건부) 직렬화 3종 비교 실험

### Non-goals
- 통계표 검색·추천 (2차 RAG)
- 차트 생성, 연속 대화, 웹 UI (최종)
- 여러 통계표를 합친 분석, 가중 평균
- 지역통계

## Risks

- HCX·KOSIS 접근이 늦어짐 → 샘플 응답을 저장해 두고 오프라인으로 개발
- HCX가 plan 구조화 출력을 안정적으로 못 냄 → 문장마다 [fact:id] 태그를 달게 하고 코드로 plan 추출
- 계/소계·다단 분류 표에서 필터 오류 → 게이트용 표는 단순 구조, 확대 시 표별 테스트 추가
- 골든셋 정답을 손으로 만들다 틀림 → 정답 facts도 코드로 뽑고 사람이 확인
- 팀원 역할과 겹침(데이터·평가 엔지니어) → 모듈 경계와 골든셋 담당을 팀과 합의
