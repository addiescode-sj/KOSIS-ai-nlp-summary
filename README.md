# **연구 계획서 · 국가통계 데이터 기반 AI 챗봇 및 맞춤형 통계 시각화 서비스**

---

**프로젝트명: 국가통계 데이터 기반 AI 챗봇 및 맞춤형 통계 시각화 서비스 개발**

국가데이터처(KOSIS)에서 제공하는 통계표 메타데이터와 통계 수치 데이터를 활용하여, 사용자가 자연어로 원하는 통계 정보를 검색하고 분석 결과를 확인할 수 있는 AI 서비스를 개발한다.

기존의 통계표 검색 및 안내 기능에서 나아가, **통계 수치를 AI가 분석하고 시각화 자료와 요약 결과까지 제공하는 서비스**를 구현하는 것이 최종 목표이다.

프로젝트는 총 3개 단계로 구성된다.

| 구분 | 프로젝트 | 핵심 목표 |
| --- | --- | --- |
| 실전 프로젝트 1 | 통계 수치 요약 서비스 | 통계 수치 분석 및 자연어 요약 (`summarize_stat`) |
| 실전 프로젝트 2 | 통계표 안내 챗봇 | 사용자 질의에 적합한 통계표 탐색 및 경로 안내 (`search_tables`) |
| 종합 프로젝트 | 맞춤형 통계 AI 챗봇 | 통계표 탐색부터 수치 분석·시각화(`make_chart`)까지 통합 |

본 프로젝트에서 개선하려는 부분은 다음과 같다.

- 사용자가 원하는 통계표를 찾더라도 실제 수치를 확인하고 증감률·구성비 등을 계산·분석하는 과정이 추가로 필요하다.
- 단순한 통계표 위치 안내만으로는 추이, 비교, 구성비 등 분석 결과를 즉시 확인하기 어렵다.
- 통계 데이터를 시각화하려면 별도의 차트 제작 과정이 필요하다.

## **1. Problem Definition**

### **1.1 문제점: 비즈니스 니즈**

**자연어 질문 하나로 통계표 탐색, 데이터 분석, 결과 요약 및 시각화까지 수행하는 근거 수치 고정형(Grounded) AI 서비스**를 구현한다.

국가통계포털(KOSIS)의 통계를 활용하려면 질문에 맞는 표를 찾고, 항목·시점·분류를 선택하고, 셀을 읽어 증감률이나 구성비를 계산한 뒤 차트를 만들어야 한다. 통계표 위치 안내에 더해, 실제 수치를 이해하고 활용하는 과정을 지원하는 서비스가 필요하다.

요구사항은 **자연어 질문으로 실제 통계표 수치에 근거한 답변·요약·차트를 출처와 함께 제공하는 것**이다. 모든 핵심 수치는 원본 셀 또는 원본 셀에 적용한 검증 가능한 계산식으로 추적되어야 한다. 자료가 없거나 질문을 해석할 수 없으면 숫자를 추정하지 않고, 불가 사유·가능한 범위 또는 확인 질문을 제시한다.

예시 시나리오:

**Turn 1 — 통계 수치 조회 및 분석**

사용자 질문:

> 2024년 서울특별시의 순이동 인구와 전입·전출 규모를 알려주세요.
> 

기대 답변:

> 2024년 국내인구이동통계를 확인한 결과, 서울특별시의 총전입은 [조회된 수치]명, 총전출은 [조회된 수치]명으로 순이동은 [계산된 수치]명(순유출/순유입)입니다.
> 
> 
> 출처: KOSIS / 국가데이터처 / 국내인구이동통계 / [통계표명 및 통계표 ID]
> 

**Turn 2 — 후속 시각화 요청**

사용자 질문:

> 이 통계표의 최근 5년간 추이를 차트로 만들어 주세요.
> 

기대 동작:

- 이전 대화에서 조회한 통계표와 조건(지역, 항목 등)을 대화 상태(Dialogue State)로 유지한다.
- 실제 데이터 구조(시계열 추이)에 적합한 차트 유형(꺾은선 그래프)을 선택한다.
- 차트와 주요 수치에 대한 간단한 설명을 제공한다.

대상은 제공된 인구 분야 14개 조사, 2,364개 통계표의 카탈로그다. 수치는 KOSIS OpenAPI 또는 제공된 표 파일을 통해 확보한다.

여기서 범위 밖인 ‘지역통계’는 제공 카탈로그 밖의 별도 지역통계 자료로의 확장을 뜻한다. **대상 인구 통계표 안에 존재하는 시도·시군구·읍면동 등 지역 분류는 해당 표가 실제 제공하는 수준과 시점 안에서 지원한다.** 예를 들어 시도별 인구동태와 인구밀도 비교는 연구 범위에 들어간다. 전국 단위 표에 없는 지역 값을 요구하거나 시도 표에 시군구 값을 요구하면 분류 불일치로 처리한다.

### **1.2 Task Reformulation**

초기 접근은 통계표 전체를 LLM에 넣어 값 읽기·계산·문장 작성을 한 번에 수행하는 Table QA다. 구현은 단순하지만, 값 옮김 오류·계산 오류·근거 없는 수치 생성과 입력 길이 제한이 발생할 수 있다. 이 접근을 B0 기준선으로 두고, 수치 처리와 언어 처리를 분리하는 효과를 측정한다.

최종 서비스에서는 사용자가 표를 알고 있다는 가정도 제거해야 한다. 다만 이 문제를 Stage 1부터 한꺼번에 풀지 않고 다음과 같이 나눈다.

| 하위 문제 | AI·소프트웨어 문제 유형 | 책임 단계 |
| --- | --- | --- |
| 주어진 표에서 질문 유형·항목·기간·분류 추출 | Semantic Parsing / Slot Filling | 실전 1 |
| 모호성·자료 범위·단위·결측·계산 가능성 판정 | 규칙 기반 판정 및 되묻기 | 실전 1 |
| 값 조회와 증감률·구성비·최대최소 계산 | 결정적 코드 계산 | 실전 1 |
| 근거 기반 문장 구성과 수치·조건 검증 | Data-to-Text 및 결합 검증 | 실전 1 |
| 질문에 맞는 표 검색과 답 없음 판정 | 메타데이터 RAG / Information Retrieval | 실전 2 |
| 검색·수치 모듈 연결, 차트, 후속 질문 처리 | 툴 호출·대화 상태·LangGraph 멀티에이전트 | 종합 |

### **1.3 Task 설계**

실전 1은 **통계표 하나와 질문이 이미 주어진 상황**의 수치 질의응답이다. 표 검색·차트·멀티턴·웹 서비스는 이 단계의 필수 범위에 포함하지 않는다. 입력은 표 파일 또는 조회된 표 데이터와 메타데이터이며, 이후 통합을 위한 진입점은 `summarize_stat(question, table_id) -> StatAnswer`로 설계한다. 실제 표 로딩 계약은 기존 `TableInput`과 연결한다.

실전 2는 **어느 표를 봐야 하는지 찾는 안내 챗봇**이다. `search_tables(question, k) -> list[TableCandidate]`와 별도의 답 없음 판정을 제공한다. 추천에는 조사명·통계표명·기관·수록기간·링크와 추천 근거를 포함한다. 검색된 설명문을 수치 정답으로 사용하지 않는다.

종합 단계는 두 모듈과 `make_chart(data, kind) -> Chart`를 연결한다. 최종 산출물은 답변 문장, 검증된 수치, 원본 셀 또는 계산식, 조사명·표명·표 ID·기준 시점·링크 등의 출처, 필요한 차트, 한계 또는 되묻기다. API와 스키마의 정확한 필드는 공통 계약 작업에서 확정한다.

### **1.4 이 문제가 중요한 이유**

통계 서비스의 신뢰는 수치의 정확성과 검증 가능성에 달려 있다. 유창한 답변이어도 시점이나 분류가 틀리면 사용자의 판단을 잘못 이끌 수 있다. 따라서 정확도뿐 아니라 근거 없는 수치, 잘못된 단위·조건, 거절 실패도 평가해야 한다.

또한 유사한 이름의 표가 많은 카탈로그에서는 탐색 자체가 별도 문제다. 검색·수치 처리·시각화를 모듈로 나누면 각 단계의 실패 원인을 측정할 수 있고, 검증된 계산·출처 계약을 유지하면서 다른 통계 분야로 확장할 기반을 만들 수 있다.

## **2. Background & Baseline**

### **2.1 Related Works**

아래는 연구에서 비교할 접근의 개요다. 특정 서비스의 현재 기능이나 성능을 외부에서 검증한 결과는 아니다.

- **표 직렬화 + LLM Table QA:** 표를 Markdown·JSON 등의 텍스트로 바꾸어 답변을 생성한다. 직렬화 형식, 표 길이, 모델의 읽기·계산 능력에 따른 차이를 확인할 수 있는 출발점이다.
- **Program-aided / Text-to-SQL 계열:** LLM이 질문 또는 계산 계획을 구조화하고 코드가 값을 조회·계산한다. 본 연구는 임의 코드를 자유 실행하기보다 지원된 연산과 규칙으로 계산 범위를 제한한다.
- **Data-to-Text와 사실성 검증:** 구조화된 facts를 문장으로 표현하고 값·단위·시점·분류를 확인한다. 본 연구는 수치 문장을 템플릿으로 렌더링하여 검증 대상을 명확히 한다.
- **Sparse·Dense·Hybrid 검색과 Reranking:** 표명을 직접 언급하는 질의, 개념어 질의, 여러 조건을 포함한 질의에 어떤 검색 방식이 적합한지 같은 평가셋에서 비교한다.
- **툴 호출 에이전트:** 단일 에이전트, Plan-and-Execute, 역할별 멀티에이전트가 도구 선택과 순서를 결정하도록 구성하고 정확도·비용·지연을 비교한다.
- **참고 대상:** 원안의 KOSIS AI 서비스와 `korea-stats-mcp`는 통계표 안내 및 도구 인터페이스의 조사 대상으로 둔다. 현재 기능·구현 품질을 확인한 것으로 간주하지 않으며, 관련 코드를 채택하려면 별도로 검토한다.

### **2.2 이번 프로젝트의 Baseline과 현재 상태**

**수치 요약 기준선 B0**는 통계표와 메타데이터를 읽어 최소 전처리 후 표를 직렬화하고, LLM이 직접 값 읽기·계산·문장 생성을 수행하는 방식이다. 관련 구현 위치는 `kosis_chat/`, 평가 도구는 `eval/`이다. 단순한 흐름이므로 이후 B1~B4의 개선 효과를 비교하기 쉽다.

현재 상태에 관한 근거는 문서마다 갱신 시점이 다르므로 구분한다.

| 구분 | 저장소에서 확인되는 문서상 상태 | 해석 |
| --- | --- | --- |
| B0 | 이전 스냅샷은 오프라인 MockClient 코드·44개 테스트를 기록했으며, 2026-10-22 `bash scripts/verify.sh` 재검증은 62개 테스트 통과·종료 코드 0 | 실제 HCX 기준선은 미완료이며, 오프라인 테스트를 실제 모델 품질 점수로 사용하지 않음 |
| 실데이터·EDA | 5개 표 프로파일링 및 9,513셀 캐시 기록 | current-state의 이전 스냅샷에 있던 ‘실데이터 없음’보다 진전된 작업 근거이며, 실제 수집 증거는 해당 문서 기준 |
| 골든셋 | 40건 작성, 검증기 오류 0/86·블라인드 재라벨 불일치 0/40, 웹 대조 0/66 대기로 기재 | T1-03은 진행 중이며 독립 웹 대조 완료나 최종 정답 확정으로 보지 않음 |
| 목표 기술 구성 | 본 연구계획의 설계 방향 | LangChain·LangGraph·RAG·MCP·FastAPI·Docker·통합 관측 체계 (observability, evaluation) |

따라서 **B0의 실제 모델 확정 점수는 아직 확보된 것으로 간주하지 않는다.** 이 문서의 목표치는 성능 실적이 아니다. 위 수치도 이번 연구계획서 작성 과정에서 재측정한 값이 아니라 해당 문서의 기록이다.

모델은 최종 평가 대상으로 HCX를 두고, 실제 제공 모델·입력 한도·구조화 출력 지원 여부를 확인하여 실행 설정을 확정한다. 모델과 실행 설정이 다른 결과는 별도로 표기하며, 제공 데이터의 외부 API 사용 조건도 실제 적용 전에 확인한다. 후보 모델 비교는 접근 가능한 모델이 확인될 때 수행하는 조건부 실험이다.

실전 2 검색 기준선은 한국어 토크나이저를 적용한 BM25다. 종합 단계의 비교 기준선은 동일한 검색·계산·검증 도구를 사용하는 단일 에이전트다. **LangGraph 멀티에이전트가 목표 아키텍처이며**, 단일 에이전트는 그 추가 복잡성이 어떤 효과를 내는지 확인하기 위한 비교군이다.

## **3. Proposed Method**

### **3.1 핵심 아이디어**

**숫자는 코드가 계산하고 검증하며, LLM과 에이전트는 질문 해석·도구 선택·설명 구성을 담당한다.** 수치 파이프라인은 B0에서 B1~B4로 한 번에 한 요소씩 바꾸어 평가한다.

1. **B1 전처리:** 결측 기호, 단위, 계·소계, 분류 체계와 지표 종류를 정규화한다. 원본 값과 출처 참조를 보존하며 세부 규칙은 PREPROCESSING의 R1~R9에 맞춘다.
2. **B2 질문 분석:** LLM structured output을 공통 스키마로 검사하여 유형·항목·기간·분류·모호성을 추출한다. 실제 표의 항목과 분류 목록에 매칭한 뒤 기본값 또는 되묻기를 결정한다.
3. **B3 계산:** 분자·분모·비교 기준을 먼저 정하고 답변 대상 행과 계산 근거 행을 분리해 선택한다. 합산·결측·분모 조건을 통과한 경우에만 pandas 등 결정적 코드로 5종 연산을 수행한다.
4. **B4 렌더링·검증:** LLM은 `fact_id` 선택과 설명 구성을 출력한다. 수치 문장은 facts 템플릿이 채운다. 결합 검증 V1~V5를 통과한 결과만 전달한다. 실패하면 1회 재생성하고, 계속 실패하면 유효한 facts 템플릿 답변으로 대체한다. facts 자체가 유효하지 않으면 숫자를 출력하지 않고 불가 사유를 반환한다.

facts에는 값·단위·시점·분류·지표 종류·원본 참조·계산식과 입력 facts를 보관한다. 결과에 특정 숫자가 존재하는지만 확인하는 방식으로는 다른 연도나 지역의 값을 잘못 연결한 오류를 막을 수 없으므로 조건까지 함께 검증한다.

| 결합 검증 | 검사 내용 |
| --- | --- |
| V1 참조 | 선택한 모든 `fact_id`가 존재하는지 검사 |
| V2 계산 근거 | 원본·입력 facts와 식을 따라 재계산한 값이 일치하는지 검사 |
| V3 단위 | fact와 렌더링 단위가 같은지 검사하고 %·%p 구분 |
| V4 설명 문장 | 자유 설명에 통계 수치 주장이 들어가지 않았는지 검사; 허용된 시점·연령 표기는 구분 |
| V5 조건 | 사용한 facts의 시점·분류가 질문 또는 명시한 기본값과 일치하는지 검사 |

내부 검증 통과만으로 질문에 맞는 정답을 골랐다고 보장할 수는 없다. 올바른 항목·표·조건을 선택했는지는 골든셋 정답률로 따로 평가한다.

### **3.2 Baseline 대비 무엇이 다른가**

| 구분 | B0 | B1~B4 및 종합 목표 |
| --- | --- | --- |
| 숫자 산출 | LLM이 읽고 계산 | 코드가 계산, 템플릿이 수치 문장 생성 |
| 근거 추적 | 셀·계산식 연결이 보장되지 않음 | 핵심 수치를 원본 셀 또는 검증 가능한 식에 연결 |
| 출력 검증 | 생성 결과에 주로 의존 | V1~V5, 제한된 재생성, 유효 facts 기반 대체 또는 거절 |
| 불가·모호 처리 | 프롬프트 지시에 의존 | 규칙 기반 판정, 기본값 명시, 되묻기 |
| 표 길이 | 전체 표 입력 한도에 영향 | 정규화 자료에서 필요한 행·facts를 선택; 조회 제한·처리 비용은 별도 관리 |
| 표 선택 | 표가 이미 주어짐 | 실전 2 메타데이터 검색 결과를 수치 모듈 입력으로 연결 |
| 서비스 연결 | 단일 표 실험 | 공통 스키마와 도구 계약을 통해 에이전트·API에서 재사용 |

**계산 경계:** count 계열이라도 같은 단위·시점·분류 수준의 중복 없는 말단 값이며 필요한 값에 결측이 없어야 합산한다. 시점 인구와 같은 stock은 시점 간 합산하지 않는다. flow는 빠짐없는 기간 조건을 확인한다. 율·평균·지수는 합산·단순 평균하지 않고, 가중 평균과 여러 통계표 결합은 실전 1 범위 밖으로 둔다. 구성비 분모는 같은 표·시점·단위·나머지 분류의 공식 ‘계’를 우선하고, 없으면 전체 말단 합이 유효할 때만 사용한다. 분모 0과 필요한 값의 결측은 계산 불가다.

**응답 경계:** 시점이 없으면 최신 시점, ‘최근’이면 최근 5개 시점, 생략한 분류는 유효한 ‘계’를 기본값으로 쓰되 답변에 기준을 밝힌다. ‘역대 최고’처럼 시점 자체를 찾는 질문은 전체 기간을 탐색한다. 항목이 여러 개이거나 비교 대상이 불명확하면 숫자 없이 확인한다. 일부 구간만 가용하면 그 구간을 답하고 빈 구간을 안내한다. 수치와 원인 질문이 섞이면 수치는 답하되 인과 판단은 제한한다. 상세 판정은 질문 유형 기준을 따른다.

### **3.3 Dataset & Preprocessing**

사용 데이터는 세 종류다.

- **검색용 메타데이터:** 제공 카탈로그 2,364표의 조사명·기관·표명·ID·기간·분류·단위·경로·URL 등을 이용한다. 실제 필드 가용성을 확인하고 표명·조사명·분류·항목 등의 검색 텍스트를 구성한다.
- **수치 데이터:** KOSIS OpenAPI 응답 또는 제공 파일이다. 초기에는 실제 표 하나로 전체 흐름을 검증하고, EDA의 5개 표로 확대한다. 표별 가용 시점과 분류 수준을 함께 저장한다.
- **자체 골든셋:** 수치 요약 30~40건 규모의 v0, 검색 100건 이상, 종합 단일턴·멀티턴 시나리오를 마련한다. 수치 v0는 현재 40건 작성 기록이 있으나 웹 대조 완료 전이므로 확정 평가셋과 구분한다.

EDA 대상은 `DT_1B8000F` 인구동태 추이, `DT_1B8000H` 시도별 인구동태, `DT_1B08024` 시도 인구밀도, `DT_1JC1502` 가구원수별 가구, `DT_101094A001` 누적 혼인 비율이다. EDA는 2,364표 중 인구총조사가 1,876표로 다수를 차지하고, 메타데이터 단위가 공란인 표도 있다고 기록한다. 유사 표 구별과 항목별 단위 복원이 주요 과제다.

원본 응답은 셀 단위로 정규화하고 원문 값·단위·결측 기호·시점·분류·출처를 보존한다. 원본 해시와 행 참조를 통해 셀에 연결하고 계산 fact에는 식과 입력 참조를 남긴다. `-`와 `X` 같은 기호 결측, 행 자체가 없는 시점, 행정구역 신설, 가구원수 구간 개편을 구분한다. 합계성 행을 순위 후보나 말단 합산에 섞지 않는다. 갱신일을 보존하고 잠정치 여부는 주석을 확인하기 전 단정하지 않는다.

캐시는 `data/cache/` 등 승인된 로컬 경로에 두고 데이터 버전·조회 조건·해시를 평가 실행과 연결한다. 제공 데이터·골든셋·평가 결과·API 키는 프로젝트 보관·비공개 규칙을 따른다. 관측 로그에도 원본 전체나 비밀값을 무분별하게 남기지 않는다.

골든셋은 `answerable`, `not_answerable`, `clarify`, `default_allowed`와 5개 질문 유형을 구분한다. 8개 불가 사유는 `no_period`, `no_item`, `class_mismatch`, `unit_mismatch`, `not_aggregatable`, `causal`, `missing_value`, `out_of_scope`다. 현재 v0에는 `no_item`이 빠져 있으므로 이를 모든 사유를 완전히 덮은 평가셋으로 해석하지 않는다. 상세 분포와 경계 규칙은 질문 유형 기준에 있다.

### **3.4 왜 효과가 있을 것으로 예상하는가: 검증 대상 가설**

아래는 측정 전 가설이며, B0 기준 점수를 확보한 뒤 비교한다.

- **H1:** 계산·수치 렌더링·검증을 코드로 분리하면 B0보다 계산 오류와 근거 없는 수치 주장이 줄어들 것이다.
- **H2:** 규칙 기반 가능성 판정과 명시적 되묻기는 불가 질문 처리 성능을 높일 것이다. 이때 가능한 질문의 불필요한 거절이 늘어나는지도 함께 확인한다.
- **H3:** 하이브리드 검색과 리랭킹은 개념어·복수 조건·유사 표 질의에서 BM25보다 검색 성능을 높일 수 있다. 질의 유형별 효과를 분리해 검증한다.
- **H4:** 명시적 대화 상태는 표·기간·분류를 이어받는 후속 질문의 성공률을 높일 것이다.
- **H5:** 역할을 분리한 LangGraph 멀티에이전트는 복합 요청의 도구 선택과 복구에 도움이 될 수 있다. 추가 호출로 인한 비용·지연이 증가할 수 있으므로 동일 도구를 사용하는 단일 에이전트 및 Plan-and-Execute와 비교한다.

### **3.5 목표 시스템 아키텍처**

목표 서비스는 FastAPI 진입점에서 요청을 받고 LangGraph가 대화 상태와 실행 경로를 관리하며, 역할별 에이전트가 검증된 도구를 호출하는 구조다. 아래 구성은 **설계 의도**이며 구현·연결·운영 검증은 종합 단계에서 수행한다.

| 기술·구성 요소 | 목표 책임 | 경계 |
| --- | --- | --- |
| LangChain | 모델 호출 어댑터, 구조화 출력, 검색기·도구 인터페이스 연결 | 수치 정답을 생성하거나 검증을 대체하지 않음; 실제 HCX 연동 방식은 확인 필요 |
| LangGraph 멀티에이전트 | 상태·분기·역할별 호출·되묻기·제한된 재시도와 종료 관리 | 오케스트레이션 담당; 계산·검증은 코드 도구 호출 |
| RAG | 통계표 메타데이터 색인·검색·리랭킹과 추천 근거 제공 | 숫자 정답은 API/표 원본에서 확보 |
| 결정적 수치 도구 | 정규화, 가능성 판정, 계산, facts 생성, V1~V5, 차트 데이터 검증 | 동일 입력·규칙에서 재현 가능하게 설계 |
| MCP | 선택한 검색·수치 요약·차트 도구를 명시적 스키마로 노출 | 모든 내부 함수를 자동 공개하지 않음; 검증·출처 계약을 보존 |
| FastAPI | 질의·검색·요약·차트·세션 요청의 서비스 인터페이스와 입출력 검증 | UI·에이전트가 공통 모듈을 호출하는 경계 |
| Docker | 서비스와 필요한 의존성을 패키징하여 재현 가능한 실행 제공 | 키·원본 비공개 데이터는 이미지 밖에서 주입·연결 |
| 관측·평가 | 요청별 추적과 오프라인·실제 모델 품질 평가 연결 | 운영 로그와 확정 평가 점수 구분 |

LangGraph의 역할 분담은 다음을 목표로 한다. 역할은 모든 요청마다 반드시 실행되는 고정 인원이 아니라 필요한 경로에서만 호출하는 논리적 책임이다.

1. **조정 에이전트:** 질문 의도와 대화 상태를 보고 검색·수치 응답·차트·되묻기 경로를 고른다.
2. **검색 에이전트:** 메타데이터 RAG 도구로 후보 표와 조건을 확인하고 유효한 후보가 없으면 답 없음을 반환한다. 후보가 모호하면 확인 질문으로 연결한다.
3. **수치 분석 에이전트:** 선택 표와 조건을 구조화하여 수치 도구를 호출한다. 직접 계산한 텍스트를 정답으로 제출하지 않는다.
4. **시각화 에이전트:** 검증된 결과에 맞는 차트 종류를 선택하고 차트 도구를 호출한다. 차트도 동일 facts·단위·시점·출처를 사용한다.
5. **응답 구성 에이전트:** 도구 결과를 설명 순서로 묶고 유효 facts 기반 렌더링을 요청한다. 출고 전 검증은 결정적 검사 노드가 담당한다.

공유 상태에는 요청·세션 식별자, 선택 표와 후보, 확인된 항목·기간·분류, 적용한 기본값, 도구 결과 참조, 검증 상태, 재시도 횟수를 저장하도록 설계한다. 후속 질문에서 조건을 변경하면 이전 facts를 그대로 재사용하지 않고 영향받는 조회·계산·검증을 다시 실행한다. 계획·실행 반복과 재시도에는 종료 조건과 횟수 제한을 둔다.

MCP는 도구를 다른 클라이언트에서도 일관되게 부르는 경계로 사용한다. 내부 모듈을 직접 호출하는 경로와 MCP 경로는 동일한 계산·검증 코드를 재사용한다. 네트워크 분리나 별도 MCP 프로세스 구성은 배포 설계에서 정하며, MCP 사용 자체를 정확도 향상의 근거로 삼지 않는다.

관측 체계는 요청별 검색 후보·점수, 선택 표, 구조화 조건, 도구명·파라미터, 노드 이동, 검증 실패, 재생성·템플릿 대체, 토큰·비용·지연·실행 오류를 연결한다. 특정 관측 제품이나 라이브러리 버전은 아직 확정하지 않는다. 추적 자료를 골든셋 실패 분석에 연결하여 문제가 검색·슬롯 추출·계산·렌더링 중 어디서 발생했는지 구분한다.

## **4. Experiment Design**

### **4.1 수행할 실험**

| 실험 | 비교·수행 내용 | 전제·산출물 |
| --- | --- | --- |
| E1 B0 측정 | 표 전체 직렬화 + LLM 직접 답변 | 확정 골든셋·실제 모델 실행·사람 판정 후 기준 점수 기록 |
| E2 모델 비교 | 실제 접근 가능한 HCX 후보 및 실행 설정 비교 | 제공 모델 확인 후 조건부 수행; 개발 모델 결과는 별도 표시 |
| E3 단계별 Ablation | B0 → B1 전처리 → B2 질문 분석 → B3 계산 → B4 렌더링·검증 | 동일 문항·원본 데이터·채점 규약으로 변경 요소와 전후 결과 기록 |
| E4 직렬화 비교 | Markdown 표·JSON 레코드·문장형 | 단일 표 실제 HCX E2E 게이트 통과 후에만 수행 |
| E5 검색 비교 | BM25, 임베딩, 하이브리드, 리랭커, 쿼리 재작성 | 같은 검색 골든셋에서 유형별 정확도·비용·지연 비교 |
| E6 에이전트 비교 | 단일 에이전트, Plan-and-Execute, LangGraph 멀티에이전트 | 같은 모델·도구·데이터·평가 시나리오; 역할 분리의 효과와 비용 기록 |
| E7 실패 분석 | 수치·단위·시점·분류·유사 표·거절·도구 호출 실패 | 상위 실패 유형을 개선 대상으로 정하고 회귀 확인 |

검색의 답 없음 임계값과 쿼리 재작성 설정은 개발용 문항에서 보정한다. 최종 평가용 문항에서 임계값을 다시 맞추지 않는다. 일정이 부족하면 E4와 추가 모델 실험을 이월하고 실제 표 E2E 및 필수 평가를 우선한다.

### **4.2 비교 축**

- 수치 요약: 단순 수치·추이·비교·구성비·최대최소별 B0 대비 개선량, 답변 불가·되묻기·기본값 처리 성능.
- 검색: 표명 직접 언급·개념어·조건 다수·모호·답 없음별 성능, 유사 표의 오추천 사례.
- 에이전트: 단일턴·멀티턴, 검색부터 시작하는 요청·선택 표 후속 요청·차트 요청·범위 밖 요청별 성공률.
- 비용·운영: 요청당 모델·도구 호출 수, 토큰, 비용, 지연, 재시도·대체 응답·실행 오류.

목표 멀티에이전트의 성능이 기준선보다 높다고 사전에 단정하지 않는다. 결과가 목표와 다르면 역할 수·분기·호출 방식을 단순화하는 근거와 한계를 ADR에 남긴다.

### **4.3 Evaluation Metrics 및 검증**

| 단계 | 주 지표 | 보조 지표 | 목표 또는 판정 방식 |
| --- | --- | --- | --- |
| 실전 1 | 문항 PASS 비율, 수치 정확도, 근거 없는 통계 수치 주장 건수 | 불가 질문 PASS·거절률, 불필요한 거절, 출처, 재생성·대체, 유형별 실패 | 아래 Stage 1 초안 기준 적용; B0 측정값과 구분 |
| 실전 2 | Hit@1/5/10, MRR | 답 없음 Precision·Recall·F1, 질의 유형별 분해, 비용·지연 | BM25 대비 변화 기록; 절대 합격치는 별도 합의 |
| 종합 | 최종 수치 정확도, 멀티턴 시나리오 성공률 | 툴 선택·파라미터 정확도, 출처, 차트 정합성, 요청당 비용·지연 | 단일 에이전트 대비 결과와 목표 구조의 채택 근거 기록 |

서비스 합격 기준 초안은 답변 가능 PASS 90% 이상, 답변 불가 PASS 90% 이상, 되묻기·기본값 PASS 80% 이상, 근거 없는 통계 수치 주장 0건, 답변한 문항 출처 표기 100%, 실행 실패 0건이다. 미검토 문항이 남은 잠정 점수로는 합격을 선언하지 않는다. 이 기준은 B0 자체의 합격 기준이 아니라 개선된 서비스의 목표다.

수치 정확도는 평가에 요구된 facts의 값·단위·시점·분류를 정답과 대조하여 집계한다. 원본 수량은 정확히 일치해야 하며 비율 등 반올림 허용오차는 기존 채점 규약을 따른다. %와 %p 혼동은 오답이다. 가능한 문항을 거절하면 실패로 처리하여 거절만으로 정확도를 높이지 못하게 한다. 모든 지표에 분자·분모와 평가 대상 건수를 명시한다.

최종 PASS·PARTIAL·FAIL 판정은 사람 검토로 확정한다. 정답은 원본 캐시에서 추출한 값·식과 KOSIS 웹 화면을 독립 대조하고, 가능하면 별도 검토자가 확인한다. 데이터 해시·골든셋 버전·코드 버전·모델·지원되는 생성 설정·실행 횟수·실행 시점은 실행 manifest에 기록한다. 모델이 지원하지 않는 temperature 등의 설정을 일괄 강제하지 않으며, 동일 설정에서도 모델 결과가 완전히 결정적이라고 가정하지 않는다. 확정 결과는 `docs/reports/eval-history.md`에 누적하는 기존 절차를 따른다.

소규모 v0는 오류 발견과 초기 비교에 사용하고, 개발용·최종 평가용 분리 및 표·질문 중복 점검을 거쳐 일반화 평가를 준비한다. 실패 태그는 `hallucinated_value`, `calc_error`, `wrong_unit`, `wrong_period`, `wrong_category`, `missed_refusal`, `unnecessary_refusal`, `missing_source` 등을 기존 평가 코드 명칭에 맞추어 관리한다.

**검증 게이트는 구분한다.** `bash scripts/verify.sh`는 네트워크·API 키 없이 수행하는 오프라인 코드 검증이며 실제 HCX 품질을 증명하지 않는다. 실제 통계표 하나의 HCX 전체 흐름과 확정 골든셋 점수가 Stage 1 목표를 만족해야 E2E 게이트를 통과한 것으로 본다. 종합 단계에서는 ‘표 찾기 → 수치 조회 → 차트 → 후속 조건 변경’ 시나리오를 실행하여 최종 답변과 차트의 값·단위·시점·분류·출처가 같은 facts에 연결되는지도 확인한다.
